# Test Writer

このスキルの前提は一つ：**テストの目的はカバレッジを稼ぐことではなく、実装が壊れたときに検知することだ。** カバレッジ数値は正しく検証を書いた結果として上がるものであり、それ自体を目標にすると「呼ばれたことだけ確認する」「件数だけ数える」といった薄い検証が増え、かえって壊れたコードを見逃すテストが生まれる。

## なぜテストを書く時間を惜しんではいけないか

「テストを書く時間が無い」という感覚は、多くの場合逆になっている。テストが無いと、変更のたびに手動確認や本番障害への対応で時間を失い続ける。テストは一度書けば以後の変更を高速化する基盤であり、**持続可能性**（システムが成長し続けるための土台）という観点で見ると、テストを書かないことの方が長期的に遅い。

テストの価値は、次の2種類の失敗をどちらも最小化できて初めて発揮される。

- **偽陰性**（実装が壊れているのにテストが通る）— バグを見逃す。カバレッジ主義が生みやすい失敗で、このスキルが主に防ぐ対象。
- **偽陽性**（実装は正しいのにテストが落ちる）— 頻繁に壊れるテストはやがて無視され、本当に壊れたときも「またか」と流されるようになる。過度に実装の内部詳細へ依存した検証（後述のモック化パターンに反する書き方）が主な原因。

そして変更とテストは**同じプルリクエストで出す**。後回しにすると、大抵は書かれないまま忘れられる。レビュアーも、変更とテストが揃って初めて「この変更が正しく検証されているか」を判断できる。

## 3つの保護パターン

以下はすべて、「実装が壊れたら必ず落ち、実装が正しければ絶対に落ちない」テストにするための具体的な書き方だ。各パターンの詳しい JavaScript（Jest）・Ruby（RSpec）のコード例（❌ 抜け道がある書き方 / ✅ 防御的な書き方の対比）は `references/examples.md` にまとめてある。実際にテストを書く・レビューするときは必ずそちらも参照すること。

### パターン1: 実行状態の完全検証

コールバックやモック関数の呼び出しを検証するとき、「呼ばれたこと」だけを確認する（例: `expect(fn).toHaveBeenCalled()`）と、2回発火していても、誤った引数で呼ばれていても、本来呼ばれてはいけない別のコールバック（エラー経路など）が同時に呼ばれていても、テストは通ってしまう。

**回数・引数・呼ばれてはいけない経路の3点をセットで固定する。** 「成功時に成功コールバックが1回、正しい引数で呼ばれ、失敗コールバックは一度も呼ばれない」まで書いて初めて、実行状態の抜け道がなくなる。

### パターン2: 期待値全体の検証

戻り値やレスポンスのうち一部のフィールドだけを検証する（`result.id` と `result.name` だけ見て `result.role` を見ない、など）と、検証していないフィールドの破壊やコレクションの中身の入れ替わりを見逃す。件数だけ見る検証（`items.length === 2`）も同様で、中身が別物に入れ替わっても件数が合えば通ってしまう。

**期待する構造をまるごと固定する**（`toStrictEqual` / `eq` で丸ごと比較）のが最も確実。フィールドを個別に見る必要がある場合でも、キー一覧を別途比較してキーの過不足（フィールドの欠落や意図しない追加）を検知できるようにする。

型と値の正確さにも同じ話が当てはまる。`toBeTruthy` / `be_truthy` のような曖昧マッチャは `true` だけでなく `"yes"` や `1` でも通ってしまう。**正確な値と型を明示する**（`toBe(true)` / `be true`）。

### パターン3: 外部境界のモック化

テスト対象のロジックそのものをモックしてしまう（対象メソッドをスタブしてその戻り値を検証する）と、テストはモックの設定を確認しているだけになり、実装が壊れていても気づけない。これは生成AIが書くテストで特に起きやすい失敗で、「現在の挙動が通るのに必要な最小限」だけを検証してしまう傾向がある。

**モックしてよいのはテスト対象の外側にある入力だけ**（現在時刻、乱数、外部APIのレスポンス、DBの戻り値など）。テスト対象のロジック自体は本物のまま実行し、その出力を検証する。こうして初めて、実装の誤りを実際に検知できるテストになる。

## ワークフロー

1. **何を保護するテストかを特定する。** 変更されたロジックについて、正常系だけでなく境界値・異常系（0件、空文字、上限値、エラー経路など）のうちどれを守るべきか整理する。
2. **外部境界だけを固定する（パターン3）。** テスト対象の関数・メソッド・クラス自体をモックしていないか確認する。モックしてよいのは時刻・乱数・外部I/Oなど、テスト対象の外側にあるものだけ。
3. **検証に抜け道が無いか書きながら確認する（パターン1・2）。** モックの呼び出しは回数・引数・呼ばれない経路まで。戻り値は構造全体かキーの過不足まで。曖昧マッチャは正確な値・型に置き換える。
4. **変更と同じプルリクエストでテストを出す。** テストだけ後続PRに回さない。

## 既存テストをレビューするときのチェックリスト

このスキルはテストを新しく書くときだけでなく、既存テスト（特に生成AIが書いたテスト）が防御的かどうかをレビューするときにも使える。次の兆候があれば、対応する原則に立ち返って指摘する。

- `toHaveBeenCalled()` / `have_received(:call)` だけで回数・引数を見ていない → パターン1
- 一部のフィールドだけ、または件数だけを見ている → パターン2
- `toBeTruthy` / `be_truthy` など型を問わないマッチャを使っている → パターン2
- テスト対象のメソッド自体を `spyOn` / `allow(...).to receive` でモックし、その戻り値を検証している → パターン3
- テストとセットになるはずの実装変更が、別のプルリクエストに分かれている → 同時提出の原則
