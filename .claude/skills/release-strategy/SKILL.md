# Release Strategy

このスキルの前提は一つ：**「コードを本番に配置すること」(デプロイ)と「機能をユーザーに公開すること」(リリース)は別々の出来事であり、この2つを分離できれば、大きな変更でも小さく安全に本番へ運べる。**
デプロイのたびにユーザー影響が発生する状態だと、リリースの是非とコードの正しさを同時に賭けることになり、どちらかに問題があれば両方を巻き戻すしかない。
分離できていれば、コードは先に本番へ置いておき、ユーザーへの公開だけを独立して制御できる。

## まず「フラグで隠せるか」を判定する

変更に着手する前に、この一問に答える。

**この変更は、オン/オフの条件分岐だけで公開を止められるか？**

- **隠せる** → Feature Flag で守りながらトランクベース開発を使う（下記）
- **隠せない**（画面全体の刷新、ルーティング構造の変更、フレームワーク移行など、条件分岐で挟むと逆にコードが複雑化し壊れやすくなる変更） → topic branch で本体への統合を意図的に遅延させる（下記）

判定に迷ったら、「オン/オフを切り替えるコードが、切り替えないコードより理解しにくくなっていないか」を基準にする。
フラグ分岐がその場所の可読性を壊すなら、それは「隠せない」変更のサインだ。

## Feature Flagでトランクベース開発を守る

Feature Flag は、コードの中に条件分岐を置き、環境変数や設定値でその場で動作を切り替える仕組みだ。
これがあれば、実装途中の機能をフラグオフのままメインブランチに統合できる——つまり**未完成のコードを安全に本番へデプロイできる**。

```tsx
// React
const isEnabledNewLabel = process.env.FEATURE_NEW_LABEL === 'true';
{isEnabledNewLabel && <span>NEW</span>}
```

```ruby
# Ruby
labels << 'NEW' if ENV['FEATURE_NEW_LABEL'] == 'true'
```

この仕組みの上でトランクベース開発を行う：機能全体を1本の巨大な feature ブランチで抱え込むのではなく、小さな増分を複数の PR に分割し、それぞれをフラグオフの状態でメインブランチにマージしていく。
最後の増分を実装し終えたら、フラグをオンにしてリリースする。

**この進め方が効くのは、フラグオフの間、フラグオンの間のどちらの状態も日常的にビルド・テストされ続けるからだ。**
巨大ブランチに機能を溜め込んで最後に一括統合する方式は、統合の瞬間まで「本体と噛み合うか」が検証されないため、コンフリクトや想定外の相互作用が統合直前に一気に噴き出す。
小さく刻んでフラグオフのまま先に本体へ乗せてしまえば、統合リスクは各 PR の小さな差分に分散される。

## Topic Branchでフラグで隠せない変更を扱う

条件分岐で守れない変更（画面刷新やフレームワーク移行など）は、base ブランチとの間に中間層として topic branch を置く3層構成で進める。

```
base branch ← topic branch ← 作業用の各PR
```

- 個々の PR のレビュー・統合は topic branch 上で完結させる
- topic branch は base ブランチの変更を日次などの頻度で継続的に取り込み、乖離を溜めない
- topic branch が完成し、独立して動作確認できる状態になってから、base ブランチへ反映する

この構成は、本番影響の発生を「topic branch が完成して base へ反映される瞬間」まで遅延させる。
裏を返すと、**本体との統合そのものが後ろ倒しになるトレードオフを負う**ということでもある。
取り込みを怠ると topic branch と base の乖離が拡大し、最終統合が困難になるため、日次取り込みでコンフリクトを小さく保ち続ける規律が前提になる。

Feature Flag と topic branch は排他ではない。
topic branch 内の個々の PR についても、隠せる部分があるならフラグで守っておくと、topic branch 内での統合もより安全に進む。

## 段階的ロールアウトで公開する

フラグがオンになる瞬間がユーザー影響の始点になる。
ここも一気に全ユーザーへ広げず、段階を踏む。

1. **フラグオフでデプロイする** — コードは本番にあるが、誰にも見えていない状態を作る
2. **検証環境で有効化する** — 本番相当の環境でフラグをオンにし、想定通り動くかを確認する
3. **本番環境で段階的に公開する** — 一部のユーザー・一部のトラフィックから始め、問題がなければ対象を広げる
4. **問題が出たら切り戻す** — フラグをオフに戻すだけで、コードのデプロイをやり直さずに公開を止められる

段階4が機能するのは、問題が起きたことに気づけている場合に限る。
フラグをオンにした直後に何を監視し何を鳴らすか——誰が対応し何をするべきかが明確な通知だけを選ぶ設計は `notification-design` を参照する。

この4段階の価値は、各段階が独立して失敗できることにある。
段階3で問題が見つかっても、原因調査とロールバックはフラグの切り替えだけで完結し、コードの再デプロイやロールバックを待つ必要がない。

段階1が成立するには、main へマージすればデプロイまで自動で流れる状態が前提になる。
手動デプロイのままだと「フラグオフでとりあえず本番に置いておく」ことのコストが高くなり、統合を先送りする動機が生まれてトランクベース開発が崩れる。
この自動化（リリース PR の自動生成、main マージを契機とするデプロイワークフローの分離）の実装は `ci-cd-pipeline-optimizer` の軸2を参照。

## フラグのライフサイクルとテストの原則

フラグによる切り戻しが機能するのは、**旧来のコードパスがまだ残っていて、かつそのパスに対するテストが通り続けている場合だけ**だ。
これが崩れると「フラグをオフにすれば安全」という前提そのものが嘘になる。

- フラグが有効な間は、オンの状態とオフの状態の両方をテストする。
  どちらか一方のテストしか残っていない状態は、もう一方が壊れても誰も気づけないことを意味する
- フラグ有効中に、オフ側（フォールバック側）のコードパスを削除したり壊したりしない。
  それをやった瞬間、フラグは「切り替えスイッチ」ではなく「片道の入口」になる
- 安定稼働が確認でき、「オフに戻す」シナリオが実質的に消えたら、フラグ自体とオフ側の古いコードパスを削除する。
  フラグは恒久的な設定オプションではなく、移行期間だけの足場だと考える

```ts
// フラグON時: NEWラベルが表示されることを検証
// フラグOFF時: NEWラベルが表示されないことを検証（切り戻しが機能する保証）
```

放置されたフラグは、時間が経つほど「誰もテストしていない組み合わせ」を静かに積み上げていく。
フラグを追加するタスクと、安定後にフラグを削除するタスクは、着手する時点でセットとして計画に入れておく（分割の考え方は関連スキルの `task-breakdown` を参照——Feature Flag のライフサイクルの各段階は常に別タスクとして扱う）。

## 設計・レビュー時のチェックリスト

- この変更は「フラグで隠せる」か「隠せない」か、着手前に言葉にできているか
- 隠せる変更なら、フラグ分岐がその場所の可読性を壊していないか（壊れているなら実は「隠せない」変更かもしれない）
- 隠せない変更なら、topic branch での日次取り込み計画があるか。
  乖離が拡大していないか
- 公開は段階的ロールアウトの4段階（フラグオフでデプロイ→検証環境で有効化→本番で段階公開→切り戻し）を経る計画になっているか
- フラグがオンの間、オン・オフ両方の状態がテストされているか
- フラグ有効中にフォールバック側のコードを壊していないか
- フラグを追加するタスクと同時に、削除するタスク（誰が・どの条件で判断するか）が計画されているか
