# Refactoring

このスキルの前提は一つ：**リファクタリングとは、外から見える振る舞いを一切変えずにコードの内部構造だけを変える行為だ。** 特別な期間を確保して取り組む特別なプロジェクトではなく、日々の変更の中で「いつやるか」ではなく「どうやるか」の規律の問題であり、その規律は次の3つの実践で支えられる。

1. 構造変更と振る舞い変更を分離する
2. 変更を小さく可逆な手順に分けて進める
3. 将来の削除しやすさを見据えて設計する

## なぜテストなしには成立しないか

「振る舞いが変わっていない」という主張は、それを検証するテストの強度に応じてしか信用できない。テストが弱ければ、構造を整理したつもりで実は振る舞いを壊していても、誰も気づけない。リファクタリングに着手する前に、対象のロジックが十分なテストで守られているかを最初に確認する。守られていなければ、構造を動かす前にまずテストを足す。

## 構造変更と振る舞い変更を分離する

この2つは性質がまったく異なる。**同じプルリクエストやコミットに混ぜてはいけない。** 混ぜると、テストが通ったことが「構造は壊れていない」の証拠なのか「振る舞いの変更も意図通りだった」の証拠なのか区別できなくなり、レビュアーは両方を同時に検証する羽目になる。

| 項目 | 構造変更 | 振る舞い変更 |
|------|--------|----------|
| 変わる要素 | 整理方法（名前、境界、依存関係） | 外部から見える動き |
| 検証者 | コードの読者だけで検証できる | ユーザー、APIの利用者、テストが検証する |
| 検証方法 | 既存テストが変更なしで通ることで証明できる | テストそのものを更新して新仕様を検証する |
| リスク | 低く、機械的に確認できる | 本質的にプロダクトのリスクを伴う |

両方が必要な場面では、順序を選ぶ。

- **先に構造変更 → あとで振る舞い変更**：構造をあらかじめ整理しておくことで、振る舞い変更そのものが小さく単純になる。最も安全で推奨できる順序。
- **先に振る舞い変更 → あとで構造変更**：振る舞いを急ぐ必要がある場合。ただし構造変更を「あとで」に先送りしたまま放置しないよう、別タスクとして明示的に残す。
- **構造変更をしない**：変更頻度が低い箇所は、整理にかけたコストを将来回収できる見込みが薄い。すべてのコードを同じ熱量でリファクタリングする必要はない。

## テストが出す2つの警告信号

作業中、次のどちらかが起きたら立ち止まる。

1. **「構造変更のつもりなのに、既存テストの変更を強いられた」** → それは構造変更ではなく振る舞い変更を含んでいる。分離の原則が破れているサインなので、変更をやり直すか、意図的な振る舞い変更として別コミットに切り出す。
2. **「ロジックを意図的に壊してみても、テストが落ちない」**（ミューテーションテスト的な確認） → そのテストには検証力がなく、リファクタリングの安全網として機能していない。構造を動かす前にテストを補強する。

## 小さく可逆な手順で進める

変更は小さいコミット単位で積み上げ、各コミットの後もシステムが常に動作する状態を保つ。長期間分岐したブランチで大きな並行変更を進めるのは避ける——マージのたびに差分が大きくなり、コンフリクトとレビュー負荷が増え、途中で引き返す選択肢を失う。

構造を大きく入れ替える必要があるときは、**拡張・移行・収縮（Expand / Migrate / Contract）** の3ステップに分解する。

1. **拡張（Expand）**：新しい構造を、古い構造の隣に未使用のまま追加する。この時点では誰もまだ新構造を使っていないので、既存の振る舞いに影響しない。
2. **移行（Migrate）**：利用側を一つずつ、段階的に新構造へ切り替えていく。各ステップは小さく、いつでも止められる。
3. **収縮（Contract）**：誰も古い構造を使わなくなったら削除する。この収縮が完了して初めて、リファクタリングは完了したと言える——新旧が並存したままの状態は「進行中」であり「完了」ではない。

## 将来の削除しやすさを設計する

リファクタリングは既存コードの整理だけでなく、新しく書くコードの設計にも適用される原則だ。書いた瞬間から「これは将来どうやって削除されるのか」に答えられるコードは、変更しやすいコードでもある。

**凝集度は、モジュール内の要素がどれだけ一つの目的に集中しているかの尺度で、強いほど良い。** 強さの順に並べると次のようになる。

機能的凝集 > 逐次的凝集 > 通信的凝集 > 手続き的凝集 > 時間的凝集 > 論理的凝集 > 偶発的凝集

- 機能的凝集：一つの明確な目的のために要素が集まっている（最も強く、最も削除しやすい）
- 逐次的凝集：ある処理の出力が次の処理の入力になっている
- 通信的凝集：同じデータを扱うというだけでまとまっている
- 手続き的凝集：実行順序が同じというだけでまとまっている
- 時間的凝集：同じタイミングで実行されるというだけでまとまっている
- 論理的凝集：似ているからという理由だけで汎用関数としてまとめられている
- 偶発的凝集：たまたま同じ場所に置かれているだけ（最も弱く、削除も変更も影響範囲が読めない）

凝集度が低いモジュールほど、「これを消すと何が壊れるか」を誰も正確に説明できなくなる。削除リスクを下げるために、次を実践する。

- **依存関係を明示的かつ一方向に保つ。** 循環依存や暗黙の副作用は、削除の影響範囲を追跡不能にする。
- **種類ではなく概念でコードを整理する。** `controllers/`・`services/`・`models/` のように技術的な種類（レイヤー）でディレクトリを切ると、一つの機能を削除・変更するために全レイヤーを横断調査する必要が生まれる。機能や業務ドメインといった概念ごとのサブツリーにまとめておけば、その機能を消すときの影響範囲が一目でわかる。
- **複数箇所から使われる共有抽象は、削除困難リスクとして特別扱いする。** 便利だからと安易に共有化すると、後で「誰が使っているか分からない」状態になりやすい。利用箇所を把握できる仕組み（型・参照検索・ドキュメント）を用意する。
- **死んだコードは見つけ次第すぐ消す。** コメントアウトされたコード、どこからも参照されない export、役目を終えたフラグは、放置するほど「本当に消していいか」の判断コストが上がる。

## 関連スキル

「この変更は分ける／なおす／壊すのどれで、必要な備えは揃っているか」という変更前の分類・点検は `modifiability-review` の対象。このスキルは、その中でも「振る舞いを変えずに構造だけを変える」場面に絞って、分離の徹底方法・安全な進め方・削除しやすい設計を掘り下げる。

## 進め方の要約

1. 対象のロジックが十分なテストで守られているか確認し、不足していれば先にテストを足す
2. 今回やろうとしているのは構造変更か振る舞い変更かを最初に明確にし、両方必要なら分割する（基本は構造変更を先に）
3. 作業中、テスト変更を強いられた／テストが落ちないという警告信号が出ていないか随時確認する
4. 変更は小さく可逆なコミット単位で進め、大きな入れ替えは拡張・移行・収縮の3ステップに分解する
5. 収縮（古い構造の削除）まで完了して、初めてリファクタリング完了とみなす
6. 新しくコードを書くときも「これはどう削除されるか」を自問し、凝集度と依存の向き、概念ベースの配置を意識する
