# Code Reviewer

変更をマージする前に、作成者以外の視点で確認し、その結果をもとに取り込みの判断を示す。

このスキルの中心にあるのは、**レビューのゴールは「指摘を並べること」ではなく「マージしてよいかの判断を、根拠とともに作成者に返すこと」**だという考え方だ。
だからレビューは、まず「この変更は何を達成しようとしているのか」を掴むところから始まる。達成目標が分からないまま行を追っても、要件を満たしているか・設計が妥当かは判断できず、体裁の指摘しか出せない。

そしてもう一つの軸が、**機械が判定できることと人間が判断すべきことを切り分ける**という原則だ。
規約準拠・フォーマット・変更行のテストカバレッジ・既知の脆弱性パターンは機械（linter / formatter / CI / SAST）が確実に拾う。ここを人間が一行ずつ指摘するのはレビューの浪費で、しかも機械ほど網羅的でない。
人間にしかできないのは、設計が既存構造に馴染むか・要件を本当に満たすか・そのセキュリティリスクを受容してよいか、という**判断**だ。レビューの時間はここに集中させる。

このスキルは、この2つの軸に沿ってレビューを組み立てる。

## レビューが組織にもたらすもの（なぜ丁寧にやるか）

指摘の一つひとつは、単なる品質チェックではなく次のどれかを果たしている。これを意識すると、何を書くべきか・どんな重みで書くべきかがぶれない。

- **知識の共有** — 変更を作成者以外が読むことで、その領域を知る人が増える。だから「なぜこう変わったか」を理解しようとする姿勢そのものに価値がある。
- **規約の育成** — 同じ指摘が繰り返されるなら、それは規約化・自動化すべきサインだ。人間が毎回指摘するのは非効率なので、繰り返しに気づいたら仕組み化を提案する。
- **非機能要件の確認** — テストでは落ちないセキュリティ・パフォーマンス・コンプライアンスは、人間が明示的に見ないと素通りする。
- **品質向上** — 「動く」より一段上の水準（読みやすさ・保守性）に引き上げる。ただしこれは作成者の意図を上書きする口実ではない（後述のガードレール参照）。

## ワークフロー

### 1. レビュー対象と変更意図を確定する

まず何をレビューするのかを固め、**その変更が何を達成しようとしているか**を掴む。ここを飛ばすと要件充足を判断できない。

- **PR 番号やブランチが指定されている場合**（他人の PR を見る等）：
  ```
  gh pr view <番号> --json title,body,files,commits
  gh pr diff <番号>
  ```
  PR の説明・関連 issue・コミットメッセージから、達成しようとしているゴールと受入基準を読み取る。
- **ローカルの作業差分をレビューする場合**（実装が一段落した自分の差分等）：
  ```
  git branch --show-current
  git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null | sed 's@^origin/@@'   # 既定ブランチ
  git diff <base>...HEAD          # base とのマージベースからの差分
  git log --oneline <base>..HEAD
  ```
  差分だけでは意図が分からなければ、**何を達成しようとしている差分かをユーザーに一言確認する**。憶測で要件を決めない。

**リポジトリの規約も読む。** `CLAUDE.md`・`CONTRIBUTING.md`・`.editorconfig`・linter 設定（`.eslintrc`、`ruff.toml` 等）があれば目を通す。このスキルが持ち込む一般論より、そのリポジトリで既に回っている規約が優先する。可読性の指摘は必ずこの既存規約を根拠にする。

### 2. 機械が見るものと人間が見るものを切り分ける

**先に機械チェックの状況を把握し、人力での重複指摘を避ける。** 焦点を人間の判断に集中させるためだ。

- **CI / linter / テストが既に回っているか確認する。** PR なら `gh pr checks <番号>`。ローカルなら lint/テストコマンドが分かれば実行し、分からなければユーザーに確認する。
- **機械に委ねてよいのは「体裁」だけ。** フォーマット・インデント・import 順・命名規約違反・未使用変数のような、**深刻度が一定していて linter/formatter が機械的に判定できる**ものは、CI で拾える環境なら個別に並べ立てない。未整備なら「この規約を linter に入れれば以降自動で防げる」とまとめて提案する（規約の育成）。

**ここに一つ、絶対に間違えてはいけない線がある。** 「機械でも検出できる」ことと「機械に任せてよい」ことは別だ。
セキュリティ問題（インジェクション・認可漏れ・シークレット混入）、バグ、要件未達は、SAST や高機能な linter が拾える種類のものであっても、**受容してよいかの判断が人間にしかできない**以上、レビューで正面から扱い、深刻なら `[must]` に残す。
これらを「機械が拾える指摘」として脇へ寄せると、レビューの一番大事な仕事を放棄することになる。SQL 文字列連結を見て「SAST で検出できるから」と機械委譲セクションに落とすのは典型的な誤りで、それは `[must]` のセキュリティ指摘だ。
**機械委譲は、レビューを軽くするためではなく、体裁の指摘に埋もれて重い指摘が見えなくなるのを防ぐためにある。** 判断が要るものは必ず人間が見る。

- **変更行にテストが伴っているか**はステップ3のテスト観点で扱う。カバレッジ（機械）ではなく、テストが挙動を裏付けているかという質を見る。

こうして機械に任せられる部分を外したうえで、残った**人間の判断が要る部分**に時間を割く。

### 3. 5観点でレビューする

差分を実際に読み、次の5観点で確認する。各観点の詳しいチェックリストと「なぜ見るか」は `references/review-viewpoints.md` にある。**迷ったら、あるいは指摘の粒度を上げたいときはこれを読む。** 要点だけ先に挙げる。

| 観点 | 一言で | 主眼 |
|------|--------|------|
| **機能要件** | やりたいことをやれているか | 通常ケースだけでなく境界・異常系。ゴールと受入基準に照らす |
| **非機能要件** | 動く以外の品質 | パフォーマンス・セキュリティ・コンプライアンス。テストで落ちない領域 |
| **設計・アーキテクチャ** | 既存構造に馴染むか | 責務の置き場所・依存の向き・既存パターンとの一貫性 |
| **テスト** | 挙動が裏付けられているか | 変更に対応するテストの有無と質。境界・失敗系を突いているか |
| **可読性・規約** | 次に読む人が困らないか | 命名・構造の一貫性。**リポジトリの既存規約を根拠に**、機械が拾えない部分だけ |

**読む順序に決まりはないが、機能要件と設計から入ると効率がいい。** そこに重い問題（要件を満たさない・設計が破綻している）があれば、可読性の細かい指摘は後回しになるからだ。重い指摘を優先して伝えると、作成者は手戻りの大きい方から直せる。

### 4. 指摘をラベルと修正案付きで書く

指摘は、**重みが分かるラベル**と**具体的な場所**と**どうすればよいかの提案**をセットにする。ラベルがないと作成者は「これは直さないとマージできないのか、好みの話なのか」を推測することになり、修正案がないと「では何をすればいいのか」をもう一往復かけて聞くことになる。レビューの目的は作成者の推測作業を減らすことだ。

ラベルの体系（詳しくは `references/comment-style.md`）：

- **`[must]`** — マージ前に対応が必要。要件を満たさない・バグ・セキュリティ上の問題など、これが残るとマージできないもの。
- **`[imo]`** — レビュアーの意見・提案。より良くなると思うが、作成者の判断で見送ってよい。
- **`[nits]`** — 些細な指摘（typo・軽微な体裁）。対応は任意。
- **`[ask]`** — 質問。断定できないので、まず作成者の意図を確認したいもの。

各コメントは `ファイルパス:行` の形で場所を特定し、可能なら修正例（コードや具体的な代替案）を添える。**断定できないことは `[must]` にせず `[ask]` で問う。** 「バグに見えるが、意図的な仕様かもしれない」ものを `[must]` で断定すると、作成者は正しい実装を壊す方向に誘導されうる。

### 5. レビュー結果をまとめる

個別コメントだけでなく、**全体のサマリとマージ可否の判断**を必ず添える。作成者が最初に知りたいのは「で、マージしていいのか」だからだ。

出力は次の構成にする：

```
## レビューサマリ
（この変更が何をするものか、全体としての評価を2〜3文。良い点があれば先に挙げる）

## 判断: <承認 / 要修正（[must] あり）/ 要相談（[ask] あり）>
（判断の理由を一言。[must] や未解決の [ask] があるなら何が残っているか）

## 指摘
### [must]
- `path/to/file.ts:42` — （問題）。（修正案）
### [imo]
- ...
### [ask]
- ...
### [nits]
- ...

## 機械に委ねた点 / 提案
（linter・CI で拾える／拾うべき項目があれば。規約化・自動化の提案）
```

**良い点も書く。** レビューは欠点探しではなく知識共有の場でもあるので、うまい設計・良いテストには一言触れる。これは作成者への礼儀であると同時に、「何が良いとされるか」をチームに伝える手段でもある。

### 6. GitHub に投稿する（承認が必要）

**レビュー結果を GitHub に投稿するのは、ユーザーの承認を得てから。** レビューコメントは相手（PR 作成者）に届く外向きの行為で、公開すると取り消しにくい。まずまとめた内容をユーザーに見せ、投稿してよいか確認する。

投稿する場合の手段：

- **PR 全体へのレビューとして出す**（推奨）：
  ```
  gh pr review <番号> --comment --body-file <path>   # コメントのみ
  gh pr review <番号> --request-changes --body-file <path>   # [must] があるとき
  gh pr review <番号> --approve --body-file <path>   # 問題なし
  ```
  `--request-changes` / `--approve` は明確なシグナルなので、`[must]` の有無に対応させる。どちらを使うかもユーザーに確認する。
- **行単位のコメントを付けたい場合**は `gh api` で PR review comment を作る必要がある。数が多いならまず本文にまとめて出し、必要に応じて行コメント化を提案する。

本文は一時ファイルに書いて `--body-file` で渡す（改行や記号がシェルで壊れないように）。一時ファイルはスクラッチパッドに置き、リポジトリ内に残さない。

**ローカル差分のレビュー（PR がまだない）なら、投稿先がないのでこの手順はスキップし、ステップ5の出力をそのままユーザーに返す。**

## 厳守事項（ガードレール）

- **レビューの投稿（`gh pr review` / コメント）は、ユーザーの承認を得てから実行する。** 相手に届く外向きの行為として扱う。
- **機械に委ねてよいのは体裁だけ（フォーマット・命名規約・未使用変数など）。** これらは CI/linter に委ねるか、規約化としてまとめて提案する。一方、セキュリティ・バグ・要件未達は、機械でも検出できる種類であっても人間が正面から扱い、深刻なら `[must]` に残す。「機械で拾える」を「見なくてよい」と混同しない。
- **断定できないことを `[must]` にしない。** 意図が読めないものは `[ask]` で問う。正しい実装を壊す方向に作成者を誘導しないため。
- **可読性・規約の指摘は、リポジトリの既存規約を根拠にする。** このスキルや個人の好みを規約として押し付けない。既存の慣習が、持ち込む一般論より優先する。
- **コードを書き換えない。** このスキルはレビュー（指摘と判断）が仕事で、修正の実装はしない。修正案は「こうするとよい」の提案として示し、実際に直すかは作成者が決める。ユーザーが明示的に修正まで頼んだ場合は別スキル・別作業として扱う。
- **良い点を無視しない。** 欠点だけを並べると知識共有・品質基準の伝達というレビューの価値が半減する。
- **マージ可否の判断を必ず添える。** 指摘を並べただけで終わらせない。作成者が最初に知りたいのは取り込んでよいかだ。

## 参照ファイル

- `references/review-viewpoints.md` — 5観点それぞれの詳しいチェックリストと「なぜ見るか」。機能要件・非機能要件・設計・アーキテクチャ・テスト・可読性の各観点で、具体的に何を見て何を疑うか。指摘の粒度を上げたいとき、見落としがないか確かめたいときに読む。
- `references/ai-generated-code.md` — AIエージェントが書いたコード特有の観点。存在しないAPI呼び出し、既存ユーティリティの再発明、実装に合わせて書かれたテストなど、人間のコードとは違う失敗の分布を扱う。レビュー対象の作成者がAIだと分かっているときに読む。
- `references/comment-style.md` — `[must]`／`[imo]`／`[nits]`／`[ask]` の使い分けの詳細、良いコメント・悪いコメントの対比、具体性と修正案の書き方。指摘の書き方に迷ったら読む。
