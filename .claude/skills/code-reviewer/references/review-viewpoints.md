# レビューの5観点 — 詳細チェックリスト

各観点で「何を見るか」だけでなく「なぜ見るか」を添える。
機械的に潰すためのリストではなく、どこに人間の注意を向けるべきかの地図として使う。
上から順に、機能要件と設計から見ると効率がいい。
そこに重い問題があれば可読性の細部は後回しになるからだ。

## 1. 機能要件

**なぜ見るか：** レビューはマージ判断であり、その核心は「やろうとしたことをやれているか」だ。
ここが満たされていなければ、他がどれだけ綺麗でもマージできない。

- **達成目標に照らして充足しているか。**
  PR 説明・issue・受入基準で示されたゴールを、この差分は実際に満たすか。
  目標が曖昧なら、それ自体を `[ask]` で確認する。
- **境界ケースを踏んでいるか。**
  空・0・null・最大値・最小値・1件だけ・0件のとき。
  通常ケースだけを見て「動く」と判断すると、境界で壊れる実装を通してしまう。
- **異常系・エラー処理。**
  入力が不正なとき、外部呼び出しが失敗したとき、想定外の状態のとき、どう振る舞うか。
  握りつぶしていないか、逆に過剰に握りつぶして問題を隠していないか。
- **既存の振る舞いを壊していないか（リグレッション）。**
  変更が周辺の想定を崩していないか。
  呼び出し元・呼び出し先への波及を追う。
- **競合・並行性。**
  同時実行・再入・冪等性が問題になる箇所か。
  なるなら考慮されているか。

## 2. 非機能要件

**なぜ見るか：** パフォーマンス・セキュリティ・コンプライアンスはテストで自動的には落ちない。
人間が明示的に見ないと、動くコードとして素通りする。
ここは特に人間の判断が要る領域だ。

- **セキュリティ。**
  - 入力の検証・サニタイズ（SQL/コマンド/パスインジェクション、XSS）。
  - 認証・認可の抜け（このエンドポイント/操作に権限チェックはあるか）。
  - **シークレットのハードコーディング。**
    API キー・トークン・パスワード・接続文字列が直接埋め込まれていないか。
  - 機密情報のログ出力・エラーメッセージへの露出。
  - **ただし、リスクを「受容してよいか」の判断は作成者・チームのもの。**
    レビュアーはリスクを可視化し、`[must]`（塞ぐべき）か `[ask]`（意図と受容可否を問う）かで返す。
- **パフォーマンス。**
  ループ内クエリ（N+1）、不要な全件走査、巨大データの一括ロード、計算量が入力サイズに対して跳ねる箇所。
  **ただし早すぎる最適化を強いない** — 実測やホットパスの根拠なく「速くしろ」と言わない。
- **コンプライアンス・プライバシー。**
  個人情報・規制対象データの扱いが方針に沿うか。
  監査ログ・保持期間などの要件がある領域か。
- **リソース管理。**
  ファイル・コネクション・ロックが確実に解放されるか（失敗経路も含めて）。

## 3. 設計・アーキテクチャ

**なぜ見るか：** 「動く」実装は無数にあり、そのうち「既存構造に馴染む」ものを選ぶのが設計だ。
ここは機械には判断できず、しかも後から直すコストが最も高いので、早い段階で見る価値が大きい。

- **責務の置き場所。**
  ロジックが適切な層・モジュールにあるか。
  UI にビジネスロジックが漏れていないか、逆も然り。
- **既存パターンとの一貫性。**
  同種の処理が既にある場合、そのパターンに倣っているか。
  新しいやり方を持ち込むなら、それだけの理由があるか。
  **一貫性はそれ自体が価値**で、次に読む人の学習コストを下げる。
- **依存の向き。**
  下位モジュールが上位に依存していないか。
  循環依存を作っていないか。
- **抽象の妥当性。**
  抽象化が早すぎ（1箇所しか使わないのに汎用化）でも遅すぎ（同じコードが3箇所にコピーされている）でもないか。
- **変更の波及範囲。**
  この変更が将来の変更を難しくしていないか。
  逆に、拡張しやすくなっているか。
- **公開インターフェースの設計。**
  関数・API のシグネチャは呼びやすいか。
  破壊的変更を含むなら、その影響が把握されているか。
- **変更の分類が妥当か。**
  この変更が「分ける（配置の変更）」「なおす（表現の変更）」「壊す（ユニットの削除）」のどれにあたり、それぞれに必要な備えが揃っているかは `modifiability-review` の観点で点検できる。
  特に削除を含む変更では、依存が列挙し切れているかを確認する。

## 4. テスト

**なぜ見るか：** テストは「この挙動が正しい」という主張の裏付けだ。
裏付けのない変更は、今動いていても次の変更で静かに壊れる。
カバレッジ（機械で測れる）ではなく、テストの**質**を人間が見る。

- **変更に対応するテストがあるか。**
  実装だけ足してテストがない場合、理由を確認する（テスト不要な変更なのか、書き忘れなのか）。
  原則テストは実装と同じ変更で入る。
- **テストが挙動を裏付けているか。**
  通っているだけで何も検証していないテスト（アサーションが弱い、モックしすぎて実質何も見ていない）になっていないか。
- **境界・失敗系を突いているか。**
  正常系だけでなく、機能要件で挙げた境界・異常系がテストされているか。
  バグ修正なら、そのバグを再現するテストが入っているか（入っていないと再発を防げない）。
- **テストの読みやすさ。**
  テストは仕様書でもある。
  何を検証しているのかが名前と構造から分かるか。
- **壊れやすさ。**
  実装の詳細に結合しすぎて、リファクタのたびに壊れるテストになっていないか。

テストの質を具体的にどう詰めるか（モックの呼び出し検証を回数・引数・呼ばれない経路まで固定する、期待値を構造全体で検証する、外部境界だけをモックする）は `test-writer` に詳しい。
「アサーションが弱い」と感じたら、同スキルの既存テスト用チェックリストを当てる。

## 5. 可読性・規約

**なぜ見るか：** コードは書かれる回数より読まれる回数の方がずっと多い。
次に読む人（半年後の自分を含む）が困らないかを見る。
ただし**機械が拾える部分は機械に任せ、人間は機械が見られない部分に集中する。**

- **命名。**
  変数・関数・型の名前が、それが何であるかを言い当てているか。
  誤解を招く名前（`data`、`tmp`、実態と違う名前）になっていないか。
  これは linter では拾えない、人間が見るべき典型。
- **構造の一貫性。**
  同じ種類の処理が同じ形で書かれているか。
  片方だけ違う書き方だと、読む人は「なぜ違うのか」を考えさせられる。
- **複雑さ。**
  深いネスト・長すぎる関数・多すぎる分岐。
  読み手が一度に頭に入れる量が多すぎないか。
  早期リターンや抽出で下げられないか。
- **デバッグ出力・コメントアウト・TODO の取り残し。**
  `console.log` / `print` デバッグ文、コメントアウトされた旧コード、放置された `TODO` が混入していないか。
  これらは差分に紛れやすい。
- **コメントの質。**
  「何をしているか」ではなく「なぜそうするか」が書かれているか。
  コードを読めば分かることを繰り返すコメントは不要。
  逆に、非自明な判断の背景は書かれているべき。
- **フォーマット・規約準拠は原則機械に任せる。**
  インデント・セミコロン・import 順などが linter/formatter で管理されている環境なら、人力で指摘しない。
  未整備なら「導入するとこの種の指摘が不要になる」と提案する（規約の育成）。
