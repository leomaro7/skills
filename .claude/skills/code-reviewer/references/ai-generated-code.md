# AI生成コードのレビュー観点

5観点（`review-viewpoints.md`）に加えて確認する、AI エージェントが書いたコード特有の観点。
人間が書くコードとは失敗の分布が違うため、別枠で扱う。
作成者が AI だと分かっている差分（PR の「使用したプロンプト」欄で判別できることが多い）をレビューするときに読む。

## なぜ別枠で扱うか

人間のミスは経験や集中力のばらつきから生まれ、レビュアーもその種のミスを見つけることに慣れている。
AI エージェントのミスは性質が異なり、**もっともらしく、かつ一見して気づきにくい**形を取りやすい。
構文的には正しく、命名も自然で、テストも通っているのに、存在しない API を呼んでいたり、実装に都合よく書かれたテストだったりする。
通常の観点だけでレビューすると見落としやすいので、意識して探す。

## 起きやすい失敗モード

- **存在しない API やメソッドの呼び出し。**
  もっともらしい名前のメソッドを、実在を確認せずに呼んでいることがある。
  使われているライブラリ・フレームワークのメソッドは、型定義やドキュメントで実在を確認する。
- **既存ユーティリティの再発明。**
  リポジトリ内に同等の処理が既にあるのに気づかず、似た関数を新しく書いてしまう。
  似た処理が複数箇所にできていないか、`grep` で同名・類似名の関数を探す。
- **実装に合わせて書かれたテスト。**
  `test-writer` が扱う「実行状態の完全検証」「期待値全体の検証」が弱いテストは、AI が自分の実装をなぞって書いたテストに多い。
  実装を一時的に壊してテストが落ちるか確認するのが最も確実（`test-writer` のワークフロー参照）。
- **要求されていない抽象化・スコープ拡大。**
  依頼された範囲を超えて、関連しそうな箇所まで「ついでに」書き換えていることがある。
  差分の各ハンクが、この変更のために本当に必要かを確認する。
- **コメントと実装の乖離。**
  実装を書き換えた際にコメントが更新されず、古い挙動の説明のまま残っていることがある。
  コメントが実装の説明として今も正しいかを確認する。
- **前提の取り違え。**
  複数の AI エージェントが並行して作業した場合（`agent-parallelization`）、他のタスクの前提を知らないまま進めた結果、インターフェースや設計方針が食い違っていることがある。

## 確認の仕方

- 「動くはず」で終わらせず、実際に実行して確認する。
  特に API の実在確認とテストの検証力は、読むだけでは判断しづらい
- 差分を丸ごと信用せず、各ハンクについて「この変更は依頼された範囲に含まれるか」を自問する
- PR の「使用したプロンプト」欄と実装を突き合わせ、依頼内容と実装範囲が一致しているか確認する
