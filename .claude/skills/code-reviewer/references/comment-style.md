# レビューコメントの書き方

コメントの目的は、**作成者の推測作業を最小化すること**だ。
良いコメントを読んだ作成者は、追加のやり取りなしに「何が問題で、どう直せばよく、それは必須なのか」を理解できる。
悪いコメントは、そのたびに一往復の確認を生む。

## ラベルで重みを示す

指摘には必ずラベルを付ける。
ラベルがないと、作成者は一つひとつの指摘について「これはマージをブロックするのか、単なる好みか」を推測することになる。
この推測こそがレビューを重く遅くする。

| ラベル | 意味 | マージへの影響 | 使いどころ |
|--------|------|----------------|------------|
| `[must]` | 対応必須 | ブロックする | 要件未達・バグ・セキュリティ問題。これが残るとマージできない |
| `[imo]` | 意見・提案 | ブロックしない | より良くなると思う。作成者の判断で見送ってよい |
| `[nits]` | 些細な指摘 | ブロックしない | typo・軽微な体裁。対応は任意 |
| `[ask]` | 質問 | 場合による | 断定できない。まず意図を確認したい |

**`[must]` は慎重に使う。**
乱発すると「全部が必須」に見えて重みが伝わらない。
本当にマージを止めるべきものだけに絞る。
逆に、遠慮して重要な指摘を `[imo]` にすると、直すべきものが見送られる。
判断はマージ可否という一点で行う — これが残るとマージできないなら `[must]`、そうでなければ `[imo]` 以下。

**断定できないなら `[ask]`。**
「バグに見えるが意図的な仕様かもしれない」を `[must]` で断定すると、正しい実装を壊させる恐れがある。
意図が読めないものは問いにする。

## 3つの要素をセットにする

良いコメントは **場所・問題・提案** が揃っている。

1. **場所** — `path/to/file.ts:42` の形で特定する。
   「どこかにある」では作成者が探す羽目になる。
2. **問題** — 何が問題か、そして**なぜ問題か**。
   理由があると作成者は納得して直せるし、次から自分で気づける（知識共有）。
3. **提案** — どうすればよいか。
   コード例や具体的な代替案。
   「これはダメ」で止めず、進む方向を示す。

## 良い例・悪い例

**例1：バグの指摘**

- ❌ 悪い：「ここバグってます」
  → 場所も理由も直し方もなく、作成者は3つとも聞き返すことになる。
- ✅ 良い：
  ```
  [must] `src/cart.ts:88` — 割引率が 0 のとき `price / rate` でゼロ除算になります。
  rate が 0 のケース（クーポンなし）が通常フローで発生するはずです。
  `rate === 0 ? price : price / rate` のようにガードを入れるか、
  そもそも割引後価格を別関数に分けると安全です。
  ```

**例2：設計の提案（必須ではない）**

- ❌ 悪い：「この関数は責務が多すぎる。
  分割すべき」（断定的だが必須か不明）
- ✅ 良い：
  ```
  [imo] `src/report.ts:120-190` — この関数が「集計」と「整形」の両方を持っていて、
  片方だけ再利用したい場面で使いにくそうです。`aggregate()` と `format()` に
  分けると、既存の `summary.ts` の構成とも揃います。今回のスコープ次第なので
  必須ではありません。
  ```

**例3：意図が読めないとき**

- ❌ 悪い：「[must] この early return は不要なので消してください」（意図を確認せず断定）
- ✅ 良い：
  ```
  [ask] `src/auth.ts:34` — ここで `role === 'guest'` のとき early return していますが、
  下の権限チェックも guest を弾くように見えます。二重チェックは意図的ですか？
  （防御的に残しているなら [nits] でコメントを一言、冗長なら削除でよさそうです）
  ```

## トーン

- **コードを批評し、人を批評しない。**
  「あなたは〜」ではなく「このコードは〜」。
- **良い点も書く。**
  うまい設計・良いテスト・丁寧なエラー処理には一言触れる。
  レビューは知識共有の場であり、「何が良いとされるか」を伝える機会でもある。
  欠点だけを並べると、その価値が半減する。
- **断定を避けるべき場面では和らげる。**
  確信がないのに強く言うと、作成者を誤った方向に押す。
  逆に `[must]` は明確に伝える — 遠慮して伝わらないと意味がない。
- **繰り返す指摘は仕組み化を提案する。**
  同じ種類の指摘を何度もするなら、それは linter ルールや規約に落とすべきサイン。
  個別指摘より「これを自動化しませんか」の方が長期的に効く。
