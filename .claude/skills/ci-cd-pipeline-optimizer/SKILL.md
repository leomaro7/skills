# CI/CD Pipeline Optimizer

このスキルの前提は一つ：**CI/CDの改善は「なんとなく速くする」「なんとなく自動化する」ではなく、計測してボトルネックを特定し、そこだけを変えて効果を検証するループとして回す。** 勘で複数箇所を同時にいじると、何が効いたのか分からなくなり、次の改善判断ができなくなる。

## 改善の3つの軸

CI/CDの改善は次の3つの軸のどれかに分類できる。相談を受けたら、まずどの軸の話かを切り分ける。

1. **CIを速くする** — プルリクエストのゲートとなるチェックの所要時間を縮める
2. **リリースを自動化する** — リリース作業を「手順の実行」から「レビューとマージ」に変える
3. **結果を通知する** — パイプラインの成否を、必要な相手に必要な経路で届ける

いずれも目的は開発者が変更を出してからフィードバックを得るまでの時間を縮めることであり、デプロイ回数のような結果指標を直接動かそうとしないこと（詳しくは後述）。

## 軸1: CIを速くする

### 目安と計測ループ

プルリクエストのゲートとなるパイプラインは**10分以内**を目安にする。**5分を超えたら改善を検討する対象**とみなしてよい。ただし数値だけを見て一律に手を入れるのではなく、次のループで進める。

1. ジョブごとの所要時間を計測する（GitHub Actionsならワークフローの実行時間の内訳、またはタイムスタンプ差分で計測できる）
2. 最も時間を占めているジョブ・ステップ（ボトルネック）を1つ特定する
3. そこだけを変更する
4. 変更前後の所要時間を比較して、効果があったか検証する
5. 1に戻る

複数箇所を同時に変えない。効果測定ができなくなり、次の判断材料を失う。

### 具体的な高速化手法

**キャッシュ戦略**
- 依存関係のロックファイル（`package-lock.json`、`Gemfile.lock`、`poetry.lock`等）のハッシュをキャッシュキーにし、変更がなければ再利用する
- 毎回ゼロからのインストールは純粋なオーバーヘッドなので、依存関係インストールは常にキャッシュ対象にする
- テストDBのスキーマ構築やビルド成果物など、依存関係インストール以外でも再生成コストが高い準備処理があればキャッシュ候補として洗い出す
- 具体例は `references/github-actions-examples.md` の「キャッシュ」を参照

**実行スキップ**
- ドキュメントのみの変更（`.md`ファイルや`docs/`配下のみ）では、テストジョブを走らせる必要がない
- ただし、その変更検出ワークフロー自体が必須ステータスチェックに指定されている場合は、**ワークフロー全体をスキップしてはいけない**（PRがマージ不可のまま止まる）。ワークフローは常に起動させ、内部の各ジョブ・ステップ側の条件でスキップさせる
- 具体例は `references/github-actions-examples.md` の「変更検出とスキップ」を参照

**並列化（matrix戦略）**
- テストスイートを分割し、matrix戦略で複数ジョブに同時実行させる
- 分割の総所要時間は「最も遅いシャード」で決まる。ファイル数で機械的に等分するのではなく、実行時間ベースで分配し、各シャードの完了時刻を揃えるほうが効果が大きい
- 具体例は `references/github-actions-examples.md` の「matrix並列化」を参照

**ランナー選択**
- CPU/メモリの大きいランナーは単価が上がるが、実行時間短縮によってトータルの消費分数（＝コスト）が減ることがある
- 勘で選ばず、計測ループの中で「ランナーを変えたら所要時間とコストがどう変わったか」を確認してから採否を決める

## 軸2: リリースを自動化する

目指す状態は、本番リリースが「手順を人間が実行する作業」ではなく「**レビューしてマージするだけの作業**」になること。

### 手順

1. **コミットメッセージを、後から読んで意図が伝わる文体にする。** これはリリースノートを自動生成する際の元データになるため、自動化の土台として先に整えておく価値がある
2. **リリースノートは、前回リリース以降にマージされたPRの一覧から自動生成する。** 手作業での編集を不要にし、書き漏れや記載ミスといったヒューマンエラーを減らす
3. **「リリース用PRの作成」をワークフローに任せる。** 変更をリリース対象としてまとめたPRを自動で作成させ、人間はその内容をレビューしてマージするだけにする
4. **mainブランチへのマージをトリガーに、本番デプロイを実行する別ワークフローを用意する。** リリース準備のワークフローとデプロイ実行のワークフローを分離することで、「レビュー・マージ」と「デプロイ実行」の責務が分かれ、事故が起きにくくなる

### ブランチモデルはこのスキルでは決めない

この軸が前提にするのは「**リリースPRの自動生成**」と「**mainブランチへのマージがデプロイのトリガーになっていること**」の2点だけで、どちらもトランクベース開発でもリリースブランチ運用でも同じように成立する。既存の運用があればそれを尊重し、この2点だけを崩さないようにする。

どのブランチモデルを採るか——小さな増分をFeature Flagで隠したままmainへ継続的に統合するのか、リリースブランチでリリース対象をまとめてから出すのか——は、CIの自動化ではなく「**デプロイとリリースをどう分離するか**」という別の主題に属する判断なので、`release-strategy` に従う。ここでブランチモデルを提案しない。

具体的なワークフロー例（リリースPR自動作成・mainマージ契機のデプロイ）は `references/github-actions-examples.md` の「リリース自動化」を参照。

## 軸3: パイプラインの結果を通知する

### 2つの通知経路

パイプラインの結果を届ける経路は目的が異なる2種類がある。混同しないこと。

- **PR上のステータスチェック** — レビュー中のフィードバック用。開発者がPRを見ている間に気づける
- **チャット（Slack等）への通知** — 本番デプロイの完了、スケジュール実行（定期バッチ等）の失敗など、PRの外で起きる出来事を伝える用

### 実装: 成功時も失敗時も必ず送る

デプロイジョブの末尾に `if: always()` を付けた通知ステップを1つ置き、成功・失敗どちらでも必ず実行させるのが単純で壊れにくい。具体例は `references/github-actions-examples.md` の「通知」を参照。

**なぜ成功時にも通知するのか、そもそも何を通知対象に選ぶべきかは `notification-design` が扱う。** ここではワークフローへの実装だけを担当し、設計原則を再説明しない。

## 補足: デプロイ頻度は目標ではなく結果

デプロイ頻度は、軸1（CIの高速化）・軸2（リリースの自動化）・変更を小粒に保つことといった**入力側の改善の結果として自然に上がる指標**である。相談がデプロイ頻度の数値そのものに向いている場合は、その手前にある軸1・軸2のどこにボトルネックがあるかへ話を引き戻す。

**指標を直接の目標に据えると数値最適化そのものが目的化する（グッドハートの法則）という一般則と、その回避策は `development-productivity` が扱う。**

## 診断の進め方

相談を受けたら、次の問いで軸を切り分けてから該当セクションに進む。

1. **困っているのは何か** — 「PRのチェックが遅い」→軸1 / 「リリース作業が手作業で大変」→軸2 / 「デプロイが失敗しても気づけない」→軸3 / 「デプロイ頻度を上げたい」→補足の観点を先に共有した上で軸1・2に誘導
2. **軸1なら**: 現状のパイプライン所要時間を確認できるか（ワークフロー実行履歴、ジョブごとの時間）。無ければまず計測から始める
3. **軸2なら**: 現在のブランチモデルとデプロイ手順を確認する。人手でやっている手順のうち「リリースノート作成」「リリース対象の確定」「デプロイの実行」のどこが自動化されていないかを特定する
4. **軸3なら**: 現在通知しているのは失敗時のみか、成功時も含むか。PR上のチェックとチャット通知のどちらが必要な場面かを確認する
