# Agent Parallelization

このスキルの前提は一つ：**複数の AI エージェントを並行させる価値は分離の質でしか実現しない。**
分離が甘いと、並行させることで得られるはずの時間短縮が、コンフリクトの後始末や統合の手戻りで消えてしまい、直列にやった方が速かったという結果になる。

`task-breakdown` は依存関係を整理して「並列実装できる単位」を見つけるところまでを扱う。
このスキルは、その単位を実際に複数のエージェントへ渡し、同時に走らせ、結果を1本の変更に統合するところを扱う。

## Step 1: 並列化してよいかを確認する

並列化の候補は、`task-breakdown` の3ステップ判定（独立性→完結性→revert 影響）を通過したタスクに限る。
**判定基準は同じもので、並列化のためだけに緩めない。**
独立性の判定に落ちるタスクを無理に並行させると、後述の分離をどれだけ丁寧にやっても統合時に必ず衝突する。

加えて、並列化には調整コストがかかる。
次のいずれかに該当するなら、並列化せずに直列で進める方が速い。

- タスクが2〜3個程度で、逐次でも数分〜十数分で終わる規模
- 各タスクが触るファイルの見当がつかず、独立しているかどうか自体が不確かな段階
- タスク同士の情報交換（片方の実装結果を見てもう片方の方針を決める、など）が発生しそうな場合

## Step 2: 作業ツリーを分離する

**同じ作業ツリーで複数のエージェントを走らせてはいけない。**
通常の git コンフリクト（コミット同士がぶつかる）より始末が悪い問題が起きる——片方のエージェントが編集の途中で保存したファイルを、もう片方が読み込んで別の変更を重ねてしまう。
ファイルの内容が編集完了状態か編集途中状態かをエージェント同士が知る術がないため、コンフリクトとして検出されずに壊れた状態のままコミットされることさえある。

分離の方法は `git worktree` かブランチのどちらか。

- **`git worktree`** — 同じリポジトリに対して、タスクごとに独立したディレクトリ（＝独立した作業ツリー）を作る。
  ファイルシステムレベルで分離されるので、エージェント間の干渉が原理的に起きない。
  並行数が多い、あるいは各エージェントが `npm install` のようなローカル状態を持つ場合に向く。
- **ブランチのみの分離** — 作業ツリーは1つのまま、エージェントごとにブランチを切り替えて進める。
  エージェントが完全に自律していて作業ツリーを共有しない（＝人間が1つずつ順に確認しながら進める）場合はこれでも足りるが、**本当の意味で同時に走らせるなら worktree が要る。**

どちらを選んでも、各エージェントのベースブランチは分岐した時点のものになる。
並行作業が長引くほどベースとの乖離が広がるので、時間がかかりそうな並列作業では、ベースの更新をエージェントに定期的に取り込ませるか、乖離が致命的にならないうちに統合を済ませる。

## Step 3: 自己完結したプロンプトを渡す

フレッシュなエージェントは、それまでの会話や他のエージェントの作業状況を一切知らない。
**「よろしく」で通じる相手ではない。**
渡すプロンプトには次を明示する。

- **やること** — 何を実装するか。
  `requirements-definition` の出力（目的・受入基準・非対象・制約）があれば、それをそのまま渡せる。
  曖昧な依頼をそのまま渡すと、フレッシュなエージェントは曖昧さに気づかず、もっともらしい解釈で進めてしまう。
- **触ってよい範囲・触ってはいけない範囲** — 他のエージェントが同時に担当しているファイルやディレクトリを明示する。
  ここが曖昧だと、独立しているはずのタスク同士が同じファイルを取り合う。
- **前提として知っておくべき決定事項** — 全体の設計方針や、他のタスクとのインターフェース（関数シグネチャ、データ形式など）で既に決まっていることがあれば渡す。
  ここが抜けると、後で統合するときに前提がずれていたことが判明する。
- **完了条件** — 何が確認できたら終わりか。
  テストが通ること、特定のコマンドが成功することなど、エージェント自身が自己判定できる基準を渡す。

## Step 4: 成果物を統合する

**各エージェントの「完了しました」という報告を、完了の証拠として扱わない。**
報告はエージェントが意図したことの説明であって、実際にやったことの証明ではない。
必ず差分を自分の目で読み、テストを実行してから次に進める。

- 各エージェントの差分を個別にレビューする。
  `code-reviewer` の観点に加え、フレッシュなエージェントが他のタスクの前提を知らずに進めた結果生まれるズレ（Step 3で渡した「前提として知っておくべき決定事項」との食い違い）がないかを見る。
- 統合の形は、タスクの独立性次第で選ぶ。
  互いに依存しない複数の機能なら、`pull-request-composer` の粒度基準どおり**別々の PR のまま出す**方が素直（無理に1つの PR へまとめない）。
  同じ機能の異なる部分（例：パーサーとバリデーター）で最終的に1つに統合する必要があるなら、先にマージするタスクを決め、後続のタスクはそのベースを取り込んでから出す。
- 統合後、全体を通しで動かして確認する。
  個々のタスクが単体で正しくても、組み合わせて初めて起きる不整合（インターフェースの食い違い、重複した処理）はここでしか見つからない。

## チェックリスト

- 並列化の候補は `task-breakdown` の3ステップ判定を通過しているか
- 調整コストがタスクの規模に見合っているか（2〜3個の小タスクを無理に並列化していないか）
- 作業ツリーが分離されているか（同じディレクトリで複数エージェントを走らせていないか）
- 渡したプロンプトに、やること・触ってよい範囲・前提・完了条件が明示されているか
- 各エージェントの差分を実際に読んだか（報告の要約だけで完了と判断していないか）
- 統合後、全体を通しで動作確認したか
