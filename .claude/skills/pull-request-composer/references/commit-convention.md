# コミットメッセージと PR タイトルの規約

Conventional Commits 形式でコミットメッセージと PR タイトルを書くための参照。

**最優先はリポジトリの既存の慣習。** `git log --oneline -20` で実際に使われている言語・型・形式を
確認し、それに合わせる。ここに書いた規約は、慣習が見つからないときの既定値として使う。

## 基本形

```
<型>: <要約>
```

要約は変更内容を1行で述べる。何をしたかが分かる具体性を持たせる。

| 型 | 用途 | 例 |
| --- | --- | --- |
| `feat` | 機能の追加 | `feat: プロフィール画面に通知設定を追加` |
| `fix` | バグの修正 | `fix: 日付フィルタの境界値のずれを修正` |
| `docs` | ドキュメントのみの変更 | `docs: セットアップ手順を追記` |
| `refactor` | 挙動を変えないコードの整理 | `refactor: 日付整形処理を共通関数に抽出` |
| `test` | テストの追加・修正 | `test: 境界値のテストケースを追加` |
| `chore` | ビルド設定・依存関係の更新などの雑務 | `chore: 依存パッケージを更新` |

型の選び方で迷ったとき：

- **実装とテストが同じコミットに入る場合は `feat` / `fix`。** テストは実装に付随するものなので、
  `test` を別コミットに切らない。`test` を使うのはテストだけを足す／直すとき。
- **`refactor` は振る舞いが変わらないことが前提。** 振る舞いが少しでも変わるなら `feat` か `fix`。
  この区別は粒度の判断そのものなので、迷ったら `references/granularity.md` の
  「構造変更と振る舞い変更を混ぜない」を読む。
- **`chore` は便利すぎるので使いすぎない。** 中身が説明できるなら具体的な型を選ぶ。

## 本文とフッター

要約1行だけでも成立する。変更の背景や理由を説明したいときは、空行を挟んで本文を加える。

本文には**何をしたか**ではなく**なぜそうしたか**を書く。何をしたかは差分を見れば分かるが、
なぜは差分に残らない。

```
refactor: 日付整形処理を共通関数に抽出

画面ごとに重複していた整形ロジックが3箇所で食い違っていたため、
共通関数に集約して仕様を一本化する。
```

## Semantic Versioning を併用する場合

ライブラリや API など互換性を管理する開発では、型の前にバージョンレベルを付ける形式を使うことがある。
コミットメッセージからリリースのバージョン番号を機械的に決定できるようになる。

```
<レベル>-<型>: <要約>
```

| レベル | 用途 | 例 |
| --- | --- | --- |
| `MAJOR` | 後方互換性のない変更 | `1.4.2` → `2.0.0` |
| `MINOR` | 後方互換性のある機能の追加 | `1.4.2` → `1.5.0` |
| `PATCH` | 後方互換性のあるバグ修正 | `1.4.2` → `1.4.3` |

型だけでは決まらないバージョンレベルを明示できるのが利点。破壊的変更を伴う機能追加は `major-feat`、
互換性に影響しない小さな機能追加は `patch-feat` のように書く。

破壊的変更はフッターに `BREAKING CHANGE:` を書き、利用者が何を直す必要があるかまで述べる。

```
major-feat: 通知一覧APIのレスポンスをページネーション形式に変更

1回のレスポンスで全件を返す形式では通知の増加に耐えられないため、
ページネーション付きの形式に変更する。

BREAKING CHANGE: レスポンスのトップレベルが配列からオブジェクトに変わるため、
クライアントはitems配列から通知を取得するよう修正が必要。
```

**この形式を使うかどうかはリポジトリ次第。** 既存のログに `major-` / `minor-` / `patch-` の
接頭辞が見当たらなければ、使わない。

## PR タイトル

タイトルはコミットメッセージをベースに、同じ形式で決める。

- **コミットが1つの PR** — そのコミットメッセージをそのまま使う。
- **複数のコミットを含む PR** — 変更全体を代表する型と要約を選ぶ。列挙にしない
  （`feat: Aを追加、Bを修正、Cをリファクタ` のようなタイトルは、粒度が混在しているサインでもある）。

タイトルは一覧・通知・マージ後の履歴に表示されるため、**本文を開かなくても変更内容を判別できる**
書き方に統一する。`fix: バグ修正` のような、開かないと分からないタイトルにしない。
