## 粒度とサイズは別の尺度

- **サイズ** = 変更行数・ファイル数
- **粒度** = 変更内容の一意性（1つのことに注力できているか）

分割の判断に使うのは**粒度**であって、サイズではない。

| 変更の例 | サイズ | 適切か | 理由 |
| --- | --- | --- | --- |
| 1万箇所で使われている関数名の一括リネーム | 大 | 適切 | 変更内容が一意なので1つの PR でよい |
| データ取得・加工・描画をまとめて実装 | 小〜中 | 不適切 | 異なる変更内容が混在しているので分割する |
| 20行のバグ修正＋ついでの無関係なリファクタ | 小 | 不適切 | 2つの変更が混在しているので分割する |

「差分が大きいので分けましょう」は誤った助言になりうる。逆に「小さいから1つでいい」も誤り。

## まとめるか分けるかの3チェック

境界を決めるのは凝集度。2つの作業 A・B が同じ単位に属するかは、次を順に当てて判断する。
**いずれか1つでも「まとめる」側に倒れたら、まとめる。**

1. **独立性** — A なしで B は正しく動くか。動かないなら同じ単位にする。
2. **完結性** — A は単体で意味のある、マージ可能な単位か。そうでないなら意味を持つところまでまとめる。
3. **revert 影響** — A を revert すると B も壊れるか。壊れるなら同じ単位にする。

## チェックするまでもない組み合わせ

**常にまとめる**

- 実装とそのテスト
- API エンドポイントとルーティング
- データモデルとマイグレーション

**常に分ける**

- リファクタリングと新機能
- ライブラリ更新と機能開発
- パフォーマンス改善と機能開発
- データマイグレーションと機能開発
- Feature Flag の各段階（追加 → 有効化 → 削除）
- 互いに依存しない複数の機能

## 良い単位の4条件

適切な粒度の単位は、次の4つを同時に満たす。分割案を作ったら各単位でこれを確認する。

- **壊さずにマージできる** — 単体で安全に統合でき、マージしてもアプリケーションは正常に動く。
- **テストを含んでいる** — 実装とそれを裏づけるテストは同じ単位で出す。別の単位に分けない。
- **単独で revert できる** — 巻き戻しても他の単位に影響しない。
- **一度に読み切れる** — レビュアーが中断せず読み通して全体を理解できる分量。

3つ目の「単独で revert できる」は分割案の検算に使いやすい。分けた片方だけを取り消したときに
もう片方が壊れるなら、その分け方は間違っている。

## 構造変更と振る舞い変更を混ぜない

**構造変更** = 振る舞いを変えないコードの整理（抽出・移動・リネーム）
**振る舞い変更** = 観測可能な振る舞いが変わる変更

この2つを同じ PR に入れてはいけない理由は、**レビューの検証方法が違う**ことにある。

- 構造変更だけの PR は「振る舞いは同一か」というただ1つの問いで検証できる。証拠は機械的で、
  **テストが1つも変更されておらず、すべて通っている**こと。この証拠があるので、レビュアーは
  大きな構造の差分でも素早く承認できる。
- 振る舞い変更の PR は意図に照らしてレビューされる。差分には更新されたテストが含まれ、
  レビュアーは新しい検証内容が仕様と一致しているかを見る。

混ざると両方の検証戦略が壊れる。テストが変更されているので「テストが変更なしで通っている」ことは
もはや振る舞いの保存を証明せず、レビュアーは全行について「これは振る舞いを変えるはずの行か」を
手作業で分類することになる。レビューは遅くなり、同時に信頼性も下がる。

**差分を読むときの手がかり**：実装ファイルの差分が「抽出・移動・リネーム」に見えるのに、
テストファイルの期待値が書き換わっている場合、構造変更と振る舞い変更が混ざっている疑いが強い。

**タイミングは選択であって規則ではない。** 別々の PR にするのは決まりだが、どちらを先に出すかは自由。

- **先に構造** — 今の構造がこれからの振る舞い変更を不格好にするなら、先に整える。
- **後で構造** — 急ぐとき、作業して初めて構造の問題が見えたときは、振る舞いを先に届けて直後に整理する。
- **やらない** — めったに触らないコードでは構造を直すコストが回収されない。手を付けない判断も正当。

判断材料は、そのコードがどれくらいの頻度で変更されるか。多くの変更が通る場所の構造はすぐ元を取り、
誰も再訪しない場所の構造は永遠に元を取らない。

## 判断に迷う具体例

**バグ修正のついでに気づいた命名の改善**
→ 分ける。修正を revert したいときに命名の改善まで巻き込む。ただし修正対象の行そのものの
リネームであれば、切り離す方が不自然になることもある。切り離すコストが利得を上回るなら
まとめてよく、その判断を PR 本文に一言書いておくとレビュアーが迷わない。

**新機能に必要な前準備のリファクタリング**
→ 分ける。先に構造変更だけの PR を出し、テストが変更なしで通ることを証拠にして通す。
その後、小さくなった振る舞い変更の PR を出す。

**フォーマッタや linter の一括適用**
→ 単独の PR にする。他の変更に混ぜると、実質的な差分がノイズに埋もれてレビュー不能になる。

**自動生成されたファイル（lock ファイル、スキーマ、型定義）の更新**
→ その更新を引き起こした変更と同じ単位に入れる。生成物だけを分けると、単体でマージしたときに
コードと生成物が食い違う。

**同じ関数に対するバグ修正と機能追加**
→ 3チェックを当てる。機能追加が修正の上に成り立っている（修正なしでは動かない）なら
まとめる。独立して動くなら分ける。

**設定ファイルやドキュメントの更新**
→ その変更を説明・支持するものなら同じ単位（例：新しい環境変数を使う実装と `.env.example`）。
無関係な整備なら分ける。

## 1つの PR に収まらないとき

分割の結果、複数の PR が必要になったら、**今回出すものと後続に回すものを明示する**。
ユーザーが「全部まとめて出したい」と言った場合はその判断に従うが、レビューが重くなる点は
一度伝えておく。

依存関係がある場合は順序を示す。前段がマージされてから後段を出すか、前段のブランチから
派生させてスタックさせるかは、チームの運用によるのでユーザーに確認する。

粒度を小さくすると PR の本数が増え、CI の実行回数も比例して増える。CI が遅いままだと
マージまでの待ち時間が積み重なって逆効果になるので、CI が明らかに遅い（10分超）場合は
その点にも触れてよい。
