## 粒度とサイズは別の尺度

- **サイズ** = 変更行数・ファイル数
- **粒度** = 変更内容の一意性（1つのことに注力できているか）

分割の判断に使うのは**粒度**であって、サイズではない。

| 変更の例 | サイズ | 適切か | 理由 |
| --- | --- | --- | --- |
| 1万箇所で使われている関数名の一括リネーム | 大 | 適切 | 変更内容が一意なので1つの PR でよい |
| データ取得・加工・描画をまとめて実装 | 小〜中 | 不適切 | 異なる変更内容が混在しているので分割する |
| 20行のバグ修正＋ついでの無関係なリファクタ | 小 | 不適切 | 2つの変更が混在しているので分割する |

「差分が大きいので分けましょう」は誤った助言になりうる。
逆に「小さいから1つでいい」も誤り。

## まとめるか分けるかの判定基準

「独立性→完結性→revert 影響」の3ステップ判定、常にまとめる／常に分ける組み合わせ、良い単位の4条件は `task-breakdown` を正典とする（同スキルの「タスクをまとめるか分けるか判定する」節と「良いタスクの条件」節）。
PR 単位の粒度もタスク分解の粒度も同じ判定基準を使うため、ここに複製しない。

タスク分解の段階で使った基準と、実際の差分を PR に切り分ける段階の基準がずれていたら、実装中に増えた変更が混ざったサインとして扱う（`SKILL.md` のステップ2に既述）。

## 構造変更と振る舞い変更を混ぜない

構造変更（振る舞いを変えないコードの整理）と振る舞い変更（観測可能な振る舞いが変わる変更）を同じ PR・同じコミットに混ぜてはいけない理由、両者で検証方法が違う仕組み、どちらを先に出すかの判断材料は `refactoring` を正典とする（同スキルの「構造変更と振る舞い変更を分離する」節）。

**差分を読むときの手がかり**：実装ファイルの差分が「抽出・移動・リネーム」に見えるのに、テストファイルの期待値が書き換わっている場合、構造変更と振る舞い変更が混ざっている疑いが強い（ステップ1の診断シグナルとも対応する）。

## 判断に迷う具体例

**バグ修正のついでに気づいた命名の改善** → 分ける。
修正を revert したいときに命名の改善まで巻き込む。
ただし修正対象の行そのものの リネームであれば、切り離す方が不自然になることもある。
切り離すコストが利得を上回るなら まとめてよく、その判断を PR 本文に一言書いておくとレビュアーが迷わない。

**新機能に必要な前準備のリファクタリング** → 分ける。
先に構造変更だけの PR を出し、テストが変更なしで通ることを証拠にして通す。
その後、小さくなった振る舞い変更の PR を出す。

**フォーマッタや linter の一括適用** → 単独の PR にする。
他の変更に混ぜると、実質的な差分がノイズに埋もれてレビュー不能になる。

**自動生成されたファイル（lock ファイル、スキーマ、型定義）の更新** → その更新を引き起こした変更と同じ単位に入れる。
生成物だけを分けると、単体でマージしたときに コードと生成物が食い違う。

**同じ関数に対するバグ修正と機能追加** → 3チェックを当てる。
機能追加が修正の上に成り立っている（修正なしでは動かない）なら まとめる。
独立して動くなら分ける。

**設定ファイルやドキュメントの更新** → その変更を説明・支持するものなら同じ単位（例：新しい環境変数を使う実装と `.env.example`）。
無関係な整備なら分ける。

## 1つの PR に収まらないとき

分割の結果、複数の PR が必要になったら、**今回出すものと後続に回すものを明示する**。
ユーザーが「全部まとめて出したい」と言った場合はその判断に従うが、レビューが重くなる点は 一度伝えておく。

依存関係がある場合は順序を示す。
前段がマージされてから後段を出すか、前段のブランチから 派生させてスタックさせるかは、チームの運用によるのでユーザーに確認する。

粒度を小さくすると PR の本数が増え、CI の実行回数も比例して増える。
CI が遅いままだと マージまでの待ち時間が積み重なって逆効果になるので、CI が明らかに遅い（10分超）場合は その点にも触れてよい。
