# Pull Request Composer

作業中の差分をレビューしやすいプルリクエストに仕立てる。

このスキルの中心にあるのは、**プルリクエストの良し悪しは差分の大きさではなく「変更内容が一意か」で決まる**という考え方だ。
1万箇所の一括リネームは巨大でも一意なので1つの PR でよく、20行のバグ修正にリファクタが混ざっていれば小さくても分割する。
焦点の絞られた差分はレビュアーの頭に収まるのでレビューが数分で終わり、後回しにされず、revert も原因特定も容易になる。
逆に複数の変更が混ざった PR はレビュアーの認知負荷を上げ、レビューが滞り、ブランチが長生きして conflict が積み上がる負の循環を生む。

だからこのスキルは「差分を診断して分ける」ことに最も時間を使い、本文の生成はその結果を書き写す作業として扱う。

## 前提条件

開始前に確認する。満たしていなければ解消するか、ユーザーに伝えて止まる。

- **カレントディレクトリが Git リポジトリであること。** `git rev-parse --show-toplevel` で確認し、以降はリポジトリルートを基準に操作する。
- **リモートが GitHub であること。** `git remote get-url origin` で確認する。GitHub 以外（GitLab など）ならこのスキルは対象外なので、その旨を伝えて止まる。
- **`gh` がインストール・認証済みであること。** `gh auth status` で確認する。
  - 未インストールなら OS に応じて案内する（macOS/Linux: `brew install gh`、Windows: `winget install GitHub.cli`）。インストールはユーザーの承認を得てから実行する。
  - 認証はユーザー自身の操作が必要なので、`! gh auth login` をプロンプトで実行するよう案内する。
- **シークレット/PII スキャナが実行可能であること。** `pre-commit-scrubber` スキルの `scripts/scan.py` を、ユーザー階層（`~/.claude/skills/`）とリポジトリ内（`.claude/skills/`）の両方から探す。Python（`python3`／無ければ `python`）も要る。
  - 見つからない、または Python が無い場合は**黙って飛ばさない。** その事実をユーザーに伝え、「スキャンなしで PR まで進めてよいか」を明示的に確認する。承認が得られなければ止まる。

## ワークフロー

### 1. 状態を把握する

まず今どうなっているかを掴む。ここを飛ばすと、既にコミット済みの変更を二重にコミットしようとしたり、ベースブランチを取り違えたりする。

```
git status -s
git branch --show-current
git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null | sed 's@^origin/@@'   # 既定ブランチ
git diff --stat                    # 未ステージ
git diff --cached --stat           # ステージ済み
git log --oneline origin/HEAD..HEAD 2>/dev/null   # このブランチの未 push コミット
```

判断すること：

- **ベースブランチ。** 既定ブランチ（通常 `main`）を基準にする。スタックした PR（前段の PR のブランチから派生している）ならユーザーに確認する。
- **現在のブランチが既定ブランチそのものの場合**、作業用ブランチを切る必要がある。ブランチ名を提案してユーザーの承認を得てから `git switch -c <名前>` する。
- **既にコミット済みの変更がある場合**、それも診断対象に含める。ただし履歴の書き換え（`git reset --soft` によるコミットのやり直しなど）は取り返しがつきにくいので、**提案に留めて必ず承認を得る**。まだ push していないコミットに限る。

**リポジトリの慣習も読む。** `git log --oneline -20` でコミットメッセージの言語（日本語か英語か）と形式（Conventional Commits を使っているか、型に何を使っているか）を確認し、既存の慣習に合わせる。このスキルが持ち込む規約より、そのリポジトリで既に回っている規約が優先する。

### 2. 粒度を診断する

差分の中身を実際に読む。`--stat` だけでは変更内容が一意かどうかは判断できない。

```
git diff
git diff --cached
```

読んだうえで、差分を**論理単位**に切り分ける。判断基準は `references/granularity.md` に詳しくまとめてあるので、迷いが出たら参照する。要点だけ先に挙げると：

- **常に分ける**：リファクタリングと新機能／ライブラリ更新と機能開発／パフォーマンス改善と機能開発／互いに依存しない複数の機能。
- **常にまとめる**：実装とそのテスト／API エンドポイントとルーティング／データモデルとマイグレーション。
- **迷ったら小さく分割する。** 小さく出して後から粒度を大きくする方が、大きく作った PR を後から分割するより簡単だから。

診断で特に見るべきシグナル：

- **構造変更（振る舞いを変えないコードの整理）と振る舞い変更が混ざっていないか。** これが混ざると、構造変更の検証手段である「テストが変更なしで通る」という証拠が失われ、レビュアーは全行を手作業で分類する羽目になる。テストファイルの差分の有無が良い手がかりになる。
- **実装があるのにテストの差分がないか。** テストは実装と同じ PR で出すのが原則なので、無ければ理由を確認する（テスト不要な変更なのか、書き忘れなのか）。
- **差分が大きいこと自体は分割の理由にならない。** 一括リネーム・自動生成物の更新・フォーマッタ適用は、大きくても一意なのでそのまま1つの PR でよい。

### 2.5. シークレット/PII をスキャンする（必須ゲート）

**分割案を出す前、まだ何も `git add` していないこの時点で必ず走らせる。** ステップ4以降は論理単位ごとに `git add` と `git commit` を繰り返すため、差分全体をまとめて検査できるタイミングはここが最後になる。コミットしてしまえば、テキストを直してもシークレットは履歴に残る。

`pre-commit-scrubber` のスキャナを直接実行する（スキル本体を起動するのではなく、スクリプトを1本走らせる）。

```
ROOT=$(git rev-parse --show-toplevel)
SCAN=$(ls ~/.claude/skills/pre-commit-scrubber/scripts/scan.py \
          "$ROOT"/.claude/skills/pre-commit-scrubber/scripts/scan.py 2>/dev/null | head -1)
python3 "$SCAN" --repo "$ROOT"
```

終了コードで分岐する。

- **0（検出なし）** — ステップ3へ進む。
- **1（検出あり）** — **ここで止まる。** 分割案の提示にもコミットにも進まない。検出内容をファイル別・カテゴリ別にユーザーへ提示し、`pre-commit-scrubber` の human review 手順（検出ごとに fix／reject／defer を人間が選ぶ）に従う。承認された修正を適用し、再スキャンがクリーンになってからステップ3に戻る。
  **実在のクレデンシャルはテキスト置換だけでは安全にならない。** 発行元でのローテーション／失効が要る。ユーザーがローテーション完了、または意図的な保留を確認するまでコミットに進まない。
- **2（環境エラー）／スキャナが見つからない** — 前提条件の判断に戻る。

**スキャナには構造的な死角がある。** 決定的に拾えるのは正規表現でマッチする SECRET と PII、および `.scrub-glossary` に登録済みの語だけで、**未登録の組織名・案件コードネーム・社内ホスト名・チケット接頭辞は見えない。** ステップ2で差分を読む際に自分の目でも確認し、見つけたものはスキャナの検出と同じゲートで扱う。検出ゼロという結果はこの死角を保証しない。

### 3. 分割案を提示して承認を得る（必須チェックポイント）

**ここで必ず一度止まる。** コミットの分け方は作者の意図に依存するので、勝手に確定しない。

提示する内容：

1. **診断結果** — 変更内容が一意か、混在しているか。混在ならどの基準で分けたのか。
2. **論理単位ごとの内訳** — 各単位に含まれるファイル（同一ファイル内で分ける場合はどの箇所か）とコミットメッセージ案。
3. **PR をいくつ出すか** — 1つの PR にまとめるか、複数に分けるか。複数に分ける場合、今回出すのはどれで、残りは後続の PR になることを明示する。
4. **後続に回す差分をどこに置くか** — ステップ4.5 の選択肢（未コミットのまま／別ブランチ／stash）のどれを使うか。ここを曖昧にしたまま進めると差分が行方不明になる。

コミットメッセージは Conventional Commits 形式で書く。型の選び方と本文の書き方は `references/commit-convention.md` を参照する。

提示例：

```
差分に2つの変更内容が混在しています。分割を提案します。

【1】fix: 日付フィルタの境界値のずれを修正
  - src/filters/date.ts（比較演算子の修正）
  - src/filters/date.test.ts（境界値のテスト追加）

【2】refactor: 日付整形処理を共通関数に抽出
  - src/utils/format.ts（新規）
  - src/views/order.tsx, src/views/user.tsx（呼び出しに差し替え）

【2】はバグ修正のついでに入った構造変更です。混ぜるとテストの差分が
両方に跨るため「テストが変更なしで通る」という構造変更の検証ができません。
【1】を今回の PR にして、【2】は後続の PR に分けることを推奨します。

この分け方で進めてよいですか？
```

ユーザーが別の分け方を望んだらそれに従う。粒度は最終的に作者とレビュアーの合意で決まるもので、機械的な基準が作者の判断を上書きするものではない。

### 4. 論理単位ごとにコミットする

承認された分け方でコミットする。

ファイル単位で分けられるなら単純に：

```
git add <paths>
git commit -m "<型>: <要約>"
```

**同一ファイル内で変更を分ける必要がある場合、`git add -p` は対話的で使えない。** 代わりにパッチを経由する：

```
git diff -- <file> > /tmp/all.patch     # 差分を書き出す
# 目的の単位に属する hunk だけを残したパッチファイルを作る
git apply --cached unit1.patch          # インデックスにだけ適用
git diff --cached --stat                # 意図どおりか確認してからコミット
git commit -m "<型>: <要約>"
```

**同じ行の中で2つの変更が絡み合っている場合、hunk 分割では切り離せない。** 典型は、関数を抽出すると同時にその中の条件を変えているケース。この場合は、
**片方だけを含むバージョンを手で書き直す**しかない。構造変更を先に出すなら、
振る舞いを完全に保存した抽出版を書いてコミットし、振る舞い変更はステップ4.5の手順で退避する。
**書き直しに手を付ける前に、ステップ4.5 の手順1（元のワークツリーをパッチとして書き出す）を先に済ませる。**
上書きしてから退避しようとしても、そのときには元の内容が残っていない。
**検算は「構造変更のコミットにテストファイルの差分が1行も含まれていないこと」。** 含まれていたら
まだ振る舞い変更が混ざっている。

各コミットの後に `git status -s` で残りを確認し、想定外のファイルが取り残されていないか見る。

**コミット後、テストが通ることを確認する。** 特に分割した場合、途中のコミットだけでも壊れていない（単体でマージしても動く）ことが重要になる。リポジトリのテストコマンドが分かれば実行し、分からなければユーザーに確認する。

### 4.5. 後続に回す差分を退避する

分割した結果、今回の PR に含めない差分が残る。**これを失わないことが最優先。**
ユーザーが書いたコードを、意図しない混入に見えたとしても勝手に捨ててはいけない。
それが事故なのか意図的な変更なのかを判断できるのは作者だけで、こちらの推測で `git checkout` や
`git restore` を実行すると、作者の作業が黙って消える。

残差分の置き方は、今回の PR を出した後にどうしたいかで選ぶ。**どれを選んだかは必ずユーザーに伝える。**

- **ワークツリーに未コミットで残す（既定）** — 今回の PR の単位だけをコミットし、残りは触らない。
  最も単純で、作者が次に何をするか決めやすい。ブランチを切り替える必要がないときはこれでよい。
- **base から別ブランチを切って移す** — 残差分が今回の PR に依存せず、並行してレビューに出せるとき。
  `git stash push -u -m "<何の差分か>"` で退避 → `git switch -c <新ブランチ> <base>` →
  `git stash pop` → コミット。並行して2つの PR を出せる状態になる。
  **これが使えるのは、残差分がそのまま切り出せるとき**（ファイル単位・hunk 単位で分けられた場合）。
- **stash に退避したまま残す** — 今回の PR に集中したいが、ワークツリーは綺麗にしたいとき。
  **必ず `-m` でメッセージを付け、stash 名をユーザーに伝える。** 名前のない stash は忘れ去られる。

意図しない混入だと強く疑われる場合（例：リファクタのはずが条件が消えている）でも、
**やることは「元に戻す」ではなく「切り離してユーザーに問う」。** 混入分を退避したうえで、
「これは意図した変更ですか？ 意図的なら後続の PR に、事故なら破棄してください」と尋ねる。

**手で書き直して分けた場合（ステップ4の「同じ行の中で絡み合っている」ケース）は、stash が使えない。**
stash は書き直し前の HEAD を基準に作られるのに、戻す先は書き直し後の HEAD になるため、
pop すればほぼ確実に競合する。この場合は次の順序で進める。

1. **書き直す前に、元のワークツリー全体をパッチとして書き出す。**
   `git diff HEAD > <リポジトリ外の作業ディレクトリ>/original.patch`。
   これがユーザーの作業の原本になる。**リポジトリの中に置かない**（誤ってコミットされる）。
2. 構造変更だけのバージョンを書き直してコミットする。
3. 振る舞い変更を作業ツリーに戻す。`git apply --3way <パス>/original.patch` を試し、
   競合したら**手で振る舞い変更だけを再適用する**。原本のパッチが残っているので、
   手作業に失敗しても元の内容は失われない。
   **`--3way` は適用の過程でインデックスにエントリを残すので、戻し終えたら `git reset` で
   unstage する。** そのままにすると、退避したはずの差分が次のコミットに巻き込まれる。
4. 戻した後、**元の状態と一致しているかを確認する**（構造変更コミット前の HEAD との
   `git diff` が、ユーザーの元の差分と同じ内容になっているか）。
5. **原本パッチの置き場所をユーザーに伝える。** 不要になったら消してよいことも添える。

**作業の途中で自分が作った一時的な stash は、内容を復元し終えたら片付けてよい。**
守るべきは「ユーザーの変更内容が最終状態のどこかに残っていること」であって、
stash エントリを永久に残すことではない。`git stash pop`（適用と同時に消える）で戻したなら
それで完了。`git stash apply` で戻した場合は、**ワークツリーやコミットに内容が乗っていることを
`git diff` で確認してから** `git stash drop` してよい。確認前に drop しない。
なお、ユーザーが自分で作った既存の stash には触らない。

### 5. PR 本文を組み立てる

テンプレートを探す。優先順位は `.github/PULL_REQUEST_TEMPLATE.md` → `.github/pull_request_template.md` → `docs/` や `.github/PULL_REQUEST_TEMPLATE/` 配下。

- **テンプレートがあれば、その見出し構成をそのまま使う。** セクションを勝手に増減しない。テンプレートはチームがレビュアーに渡す情報を決めた結果なので、埋める側が構成を変えると意味がなくなる。
- **テンプレートが無ければ**、`assets/PULL_REQUEST_TEMPLATE.md` の雛形を使って本文を書く。あわせて「このテンプレートをリポジトリに置くと、以降の PR で説明の構成が揃う」ことを提案してよい。ただしテンプレートの追加は**今回の PR とは別の変更**なので、混ぜずに別 PR として提案する。

埋め方：

- **タイトル** はコミットメッセージをベースに、Conventional Commits 形式で1行。コミットが1つならそのメッセージをそのまま使い、複数なら変更全体を代表する型と要約を選ぶ。タイトルは一覧・通知・マージ後の履歴に出るので、本文を開かなくても何をしたか分かる粒度にする。
- **チェックボックス**は、実際に確認したものだけチェックする。確認していない項目を埋めない。
  未確認なら未チェックのまま残す。**未チェックの項目が残ること自体は問題ない**が、
  なぜ確認できていないのか（テストランナーが無い、CI に任せる、など）を備考に一言書くと、
  レビュアーが「埋め忘れ」と「確認不能」を区別できる。
- **テンプレート内の HTML コメント（`<!-- 記入例 -->`）は、その項を埋めたら削除する。**
  記入者向けの指示書きなので、残すとレビュアーには読むべき情報とノイズが混在して見える。
  埋めなかった項のコメントは残してよい（後から埋める手がかりになる）。
- **「使用したプロンプト」欄**（テンプレートにある場合、または雛形を使う場合）には、
  このセッションでユーザーが実際に出した指示のうち実装方針を決めたものを記載し、モデル名は
  `claude-opus-4-8` のようにモデル ID で書く（「Claude Opus 4.8」のような通称ではなく、
  後から検索・集計できる形にする）。要約せず、実際の文面を引く。
  - **実装を AI が書いていない場合**（ユーザーが自分で実装し、PR 作成だけを依頼した場合）は、
    プロンプトを捏造せずに「実装は AI 生成ではない。PR の作成のみ AI が実施」と書く。
    この欄は AI が書いたコードをレビュアーに知らせるためのものなので、
    実装していないのに指示文を貼ると意味が反転する。
  - **人の実装を AI が書き直した場合**（分割のために構造変更だけのバージョンを作り直した等）は、
    その事実をそのまま書く。「元の実装は作成者、AI が◯◯のために△△部分を書き直した」のように、
    どの部分に AI の手が入ったかを特定できる形にする。レビュアーが厚く見るべき箇所が分かる。
  - **複数の PR に分割した場合**、元の指示は両方の変更に言及していることが多い。
    そのまま貼ると本文と食い違うので、この PR に関係する部分を引いたうえで、
    「元の指示には後続 PR の内容も含まれる」と一言添える。
  - 社内固有の名称・URL・認証情報などが混ざっていれば、その旨をユーザーに伝えて記載するか判断を仰ぐ。
- **対応 issue** は、ブランチ名やコミットメッセージから番号が拾えれば記入する。拾えなければ空欄にしてユーザーに尋ねる。

本文の下書きをユーザーに見せる。ここは承認の必須チェックポイントではないが、事実誤認（やっていない確認をチェックしている等）があれば直す機会になる。

### 6. Draft か Ready かを決める

Draft は「レビューの準備が整っていないことを明示する下書き状態」で、マージがブロックされる。次の場合は Draft を推奨する：

- 実装や設計の方向性についてフィードバックが欲しい段階（動くコードの差分を見ながら議論できるので、文書や口頭のすり合わせより認識が揃いやすい）。
- **これから実装・修正を続ける予定がある。** 作業が残っているという意味での「未完成」。
- 依存する前段の PR がまだマージされていない。

**「テストを実行できていない」ことだけを理由に Draft にしない。** 判断の軸は
「作業が残っているか」であって「こちらが検証できたか」ではない。
テストランナーが無い、環境が無いなど**こちらの都合で確認できないだけ**なら、実装としては完成しているので
Ready で出し、確認できていない事実を本文に書いてレビュアーと CI に委ねる。
一方、テストを実行して**落ちている**、あるいはテストをこれから書くつもりなら、それは作業が残っているので Draft。

**作者への未解決の問いがあり、その答え次第でこの PR の差分が変わるなら Draft にする。**
「この変更は意図的ですか？」の答えによって今出している差分を作り直すことになるなら、
レビュアーを呼ぶ前に作者が答える段階なので Draft にし、問いを本文の目立つ位置に置く。

逆に、**問いの対象がこの PR の差分に含まれていないなら Ready でよい。** 例えば混入していた
振る舞い変更を切り離して後続に回した場合、「あれは意図的でしたか？」という問いは残るが、
この PR の中身（構造変更のみ）はどちらに転んでも変わらない。申し送りとして本文に書けば足りる。

問いが「レビュアーに意見を聞きたい点」であれば、それはレビューそのものなので Ready でよい。

迷ったら Draft を選び、その理由を添えてユーザーに判断を仰ぐ。Draft から Ready への変更は
「Ready for review」を押すだけで済むが、準備不足の PR がレビュアーの時間を奪うのは取り返せない。

作業が進むほど方向転換のコストは膨らむので、迷ったら Draft で早く出す方が手戻りは小さい。

判断をユーザーに提示し、決定を仰ぐ。

### 7. push して PR を作成する

**push はユーザーが承認してから実行する。** リモートに出た時点で他人から見えるようになるため、ここは戻せない操作として扱う。

```
git push -u origin <branch>
gh pr create --base <base> --title "<title>" --body-file <path>   # Draft なら --draft を付ける
```

本文は一時ファイルに書いて `--body-file` で渡す（改行や記号がシェルで壊れないように）。一時ファイルはスクラッチパッドに置き、リポジトリ内に残さない。

**push の前に、PR 本文そのものを読み返す。** ステップ2.5 のスキャナが見るのはリポジトリの差分だけで、スクラッチパッドに置いた本文ファイルは対象外になる（`scan.py` に単一ファイルを渡すオプションは無い）。しかも「使用したプロンプト」欄はユーザー発話をそのまま貼る設計なので、**コード差分より本文のほうが機微情報を含みやすい。** 社内固有の名称・URL・認証情報・個人情報が混ざっていないかを自分の目で確認し、疑わしいものがあればユーザーに記載の可否を仰いでから `gh pr create` する。

### 8. 完了報告

ユーザーに次を伝える：

- 作成した PR の URL と、Draft か Ready か。
- 作成したコミットの一覧（`git log --oneline <base>..HEAD`）。
- **後続の PR に回した変更があれば、その内容と、どのファイルにまだ差分が残っているか。** ここを伝え忘れると作業が宙に浮く。
- レビューが滞ると小さい PR の利点が消えるので、レビュー依頼が来たら自分の作業より優先すると全体が速くなること（相手のチームにレビューを促す文脈があれば添える）。

## 厳守事項（ガードレール）

- **ユーザーが書いたコードを、どこにも残らない形で消さない。** `git checkout` / `git restore` で
  作業ツリーの変更を捨てる操作は、意図しない混入に見える変更に対しても実行しない。
  切り離して退避し、採否はユーザーに判断してもらう。
  （自分が作業用に作った一時 stash の後片付けは、内容が復元済みだと確認したうえでなら構わない。
  禁じているのは「変更内容が失われること」であって、git の操作そのものではない。）
- **こちらが混入と判断した変更を、こちらの判断で「元に戻す」形で解決しない。** 問いとして返す。
- **コミット・push・PR 作成は、ユーザーの承認を得てから実行する。** 特に分割案は必ず提示して合意を取る。
- **履歴の書き換え（`git reset`、`git rebase`、`git commit --amend`、force push）は提案に留め、承認なしに実行しない。** push 済みのコミットには原則手を出さない。
- **粒度の判断基準は差分の大きさではなく変更内容の一意性。** 大きいから分ける、小さいからまとめる、という判断はしない。
- **リポジトリの既存の慣習（コミットメッセージの言語・形式、PR テンプレートの構成）を、このスキルの規約より優先する。**
- **確認していないチェック項目にチェックを入れない。** 動作確認やテストの実施状況は事実だけを書く。
- **テンプレートの追加・修正は今回の変更と混ぜず、別の PR として提案する。**
- **シークレット/PII スキャンを通過していない差分を commit・push しない。** スキャナが使えない環境では、その事実を伝えたうえでユーザーの明示的な承認を得る。黙ってスキップしない。
