# Modifiability Review

変更容易性とは「低いコストと低いリスクで変更を受け入れられる」性質のこと。
コードベースの価値は「いま正しく動くか」ではなく「次の変更をどれだけ安く安全に受け入れられるか」で測られる。
このスキルは、変更に着手する前・レビューする際に、その変更が何を要求しているかを見極め、必要な備えが揃っているかを点検するためのものだ。

## まず変更を3つに分類する

同じ「注文履歴を直してほしい」という依頼でも、実体は次の3種類のどれかであり、それぞれ必要な備えが違う。
分類を誤ると、本来は移動するだけで済んだはずのロジックを書き直したり、逆に書き直しが必要な変更を単純な移動として扱って壊したりする。

| 分類 | 変わらないもの | 変わるもの | 典型例 |
|---|---|---|---|
| **分ける** | ユニットの入出力 | 配置・表現・量 | モーダルをページに移す、ページネーションを追加する |
| **なおす** | 概念モデル | 表現方法 | 画像を追加する、入力項目を増やす、並び順を変える |
| **壊す** | 周囲の振る舞い | ユニット本体 | 機能を廃止する、画面を削除する |

共通の例として、注文履歴を表示するコードを考える。

```tsx
// OrderItem: 表現を持つユニット
type OrderItemProps = { order: Order };
export const OrderItem = ({ order }: OrderItemProps) => (
  <li><span>{order.title}</span></li>
);

// OrderList: データを外部から受け取るだけのユニット
type OrderListProps = { orders: Order[] };
export const OrderList = ({ orders }: OrderListProps) => (
  <ul>{orders.map((order) => <OrderItem key={order.id} order={order} />)}</ul>
);

// OrderHistoryModal: 入れ物
export const OrderHistoryModal = ({ orders }: { orders: Order[] }) => (
  <Modal title="注文履歴"><OrderList orders={orders} /></Modal>
);
```

### 分ける：配置・量だけの変更

入出力そのものは変わらず、置き場所や数量だけが変わる。
たとえばモーダルをページに移しても `OrderList` は一切変更しない。

```tsx
export const OrderHistoryPage = ({ orders }: { orders: Order[] }) => (
  <PageLayout title="注文履歴"><OrderList orders={orders} /></PageLayout>
);
```

**必要な備え**: 概念的なデータモデルに沿ってユニットが切られていること。
ユニットの境界が概念とずれていると、「分ける」だけで済むはずの変更のために中身まで手を入れる羽目になる。

### なおす：表現の変更

データが指す概念自体は同じだが、見せ方や入出力の形が変わる。
商品画像を追加するなら `OrderItem` だけを直せばよく、`OrderList` や `OrderHistoryPage` は無傷のはずだ。

**必要な備え**: 変更検知の網＝静的型と自動テスト。
型を信頼できる定義元から**導出**していれば、依存先を変えた瞬間にコンパイラが影響範囲を教えてくれる。

```typescript
// ❌ 手で再宣言している型は、依存先が変わっても追随しない
type MessageArgs = { name: string } & { agent: Agent };

// ✅ 導出型は、依存先の変更がそのままコンパイルエラーとして呼び出し元に伝播する
type MessageArgs = Parameters<typeof greeting>[0] & { agent: Agent };
```

この網が張られていれば、「なおす」変更を加えたときにどこまで波及するかが機械的に見える。
**変更を加えたのにテストも型エラーも何も反応しないときは、直したつもりで直っていない可能性を疑う**——反応がないことは安全の証拠ではなく、検知網が効いていない兆候かもしれない。

### 壊す：ユニットの削除

コードを消すこと自体は簡単だが、危険なのは見えていない依存関係だ。

```diff
- import { OrderHistoryPage } from "@order-history";

  export const routes = (
    <Routes>
      <Route path="/" element={<HomePage />} />
-     <Route path="/orders/history" element={<OrderHistoryPage />} />
    </Routes>
  );
```

**必要な備え**: 依存関係が明示的で一方向であること。
「これに依存しているものは何か」に機械的に（grep やコンパイラで）答えられて初めて安全に削除できる。
消せないコード——依存先が不明で消すと何が壊れるか分からないコード——は、以後のすべての変更のコストを恒久的に押し上げ続ける。

## 分類を確認する手順

1. この変更で、ユニットの入出力・概念モデル・周囲の振る舞いのどれが変わり、どれが変わらないかを言葉にする。
2. 上の表と照らして「分ける／なおす／壊す」のどれかを決める。
   複数にまたがるなら、変更を分割できないか検討する（大きな変更ほど分類がぶれやすい）。
3. その分類に必要な備えが今のコードに揃っているかを点検する。
   - 分ける → ユニット境界は概念モデルに沿っているか
   - なおす → 型は導出されているか、その変更を検知するテストがあるか
   - 壊す → 依存元を機械的に列挙できるか
4. 備えが欠けているなら、実装そのものより先にそこを直す。
   備えを飛ばして進めると、後から「なぜこんな単純な変更にこんなに時間がかかったのか」という形で代償を払うことになる。

## 変更容易性が壊れる3つの兆候

これらは個々のコードの問題というより、チームの合意形成に起きる問題だ。
レビューや設計相談の場でこの3つのどれかが起きていないか意識する。

### 1. 前提の破綻

合意していたはずの概念モデル自体が実は違っていた、というケース。
たとえば「データは日付単位でまとまる」と合意していたのに、実際は種類別に構成されていたと分かれば、それを前提に引かれたユニット境界はすべて誤った位置にある。

**防止策**: 概念モデルに関わる変更依頼は、ただの通知としてではなく相談として扱う。
実装側が「この前提は本当に成り立つか」を確認し、必要なら押し返せる余地を残す。

### 2. ゆらぎ

同じ概念が場所によって違う仕様で決まってしまうケース。
決定のたびに変更検知の配線をやり直すことになり、変更容易性が「収束していく仕組み」ではなく「未決定の意思決定を吸収し続ける仕組み」になってしまう。

**防止策**: 一度確立したパターンは使い回す。
決定を見直すときは、新しい決定とその理由を関係者全員から見える場所に記録する（記録先と書式は `decision-records` を参照）。

### 3. 暗黙の変更

見た目や振る舞いの小さな変更は、人間には差分として認識されにくい。
とくに非機能的な細部（余白、タイミング、エラーメッセージの文言など）は「壊れて見える」失敗モードを持たないため精査の対象にならず、テストは更新されず、レビュアーには知らされず、変更した事実自体が記録に残らないまま実装に到達する。

**防止策**: 大小を問わずすべての変更を明示する。
依頼の時点で宣言し、プルリクエストの説明に振る舞いの変化として書き、変更を追跡できる粒度に保つ（詳しい分割の考え方は関連スキルの `task-breakdown` を参照）。

## レビュー時のチェックリスト

- この変更は「分ける／なおす／壊す」のどれか、レビュー対象の説明や PR 本文から判断できるか
- 「なおす」変更なら、対応するテストか型エラーが実際に反応しているか。
  反応がないなら意図した変更が本当に効いているか疑う
- 「壊す」変更なら、削除対象への依存元を機械的に洗い出した形跡があるか
- 変更の理由が「合意していた概念モデルの通知」なのか「概念モデルそのものの変更提案」なのか区別できるか。
  後者なら実装側の合意を経ているか
- 同じ概念について、他の場所と違う仕様がこっそり決まっていないか（ゆらぎ）
- 見た目や非機能の変更が PR 説明やテストに一切現れていない箇所がないか（暗黙の変更）

## 実装計画・依頼を出す側として

変更容易性は一方的なコーディング規約ではなく、依頼する側と実装する側の協働プロトコルだ。
次を心がけると、日常的な変更は軽く流しつつ、土台を壊す変更だけを事前に止められる。

1. **実装前に概念モデルを合意する**。
   モデルの範囲内に収まる変更は連絡だけで進めてよいが、モデルそのものを壊す変更は事前相談として持ちかけ、実装側に実質的な拒否権を残す。
2. **決定は一貫させ、記録する**。
   確立した概念には単一の仕様を与えて使い回し、見直すときは新しい決定と理由を双方から見える場所に書く。
3. **すべての変更を明示する**。
   大小を問わず依頼時に宣言し、PR には振る舞いの変化を説明として書く。
4. **変更検知網を維持する**。
   型は信頼できる定義元から導出し、テストは観測可能な振る舞いを検証する形にしておく。
   こうしておけば、職種をまたぐ依頼変更であっても影響範囲が機械的に浮かび上がる。
