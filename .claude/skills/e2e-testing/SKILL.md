# E2E Testing

このスキルの前提は一つ：**E2Eはユーザーが体験するのと同じ形でシステム全体を検証できる唯一のテスト層だが、実行と維持のコストが最も高い層でもある。** だからこそ「何でも検証できるから」と対象を広げず、デプロイが壊れていないか・部品同士が正しくつながっているかを守る小規模なスイートに絞り込む。バリデーションや条件分岐、コンポーネント内部のロジックはより速く安定した下位のテスト層（コンポーネントテスト・単体テスト）に任せる。

## 4つの基本原則

### 1. 主要な動線に限定する
カバレッジは次の3種類に集中させる。それ以外を広げても、コストに見合う検知力の向上は得にくい。

| 種類 | 具体例 | 理由 |
|---|---|---|
| 認証 | ログイン、会員登録 | 壊れるとユーザー全体に影響する |
| 収益動線 | 決済、注文確定 | 壊れるとビジネスに直接影響する |
| スモーク確認 | 主要画面の表示と基本操作 | デプロイそのものの破損を検知する |

この3分類はどのプロダクトにも当てはまるが、**「収益動線」が具体的にどの操作を指すかはプロダクトごとに違う。** 何が壊れたら困るかは要件側で決まっていること（受入基準・非対象）であって、コードを読んで決められるものではない。ここが曖昧なまま動線を選ぶと、スイートは「壊れたら困るもの」ではなく「テストしやすいもの」に寄っていく。受入基準が無い、または「正しく動くこと」程度にしか無い状態なら、シナリオを書き始める前に `requirements-definition` で固める。

### 2. 詳細は下位層に任せる
E2Eで「部品が正しくつながっているか」を確認したら、それ以上は追わない。バリデーションメッセージの文言、条件付き表示の分岐、コンポーネント内部の状態遷移などはコンポーネントテスト・単体テストの担当であり、E2Eに持ち込むとテストが増える割に壊れやすさばかり上がる。

### 3. デプロイ後に実行する
E2EはPull Requestのパイプラインではなく、ステージング・本番環境へのデプロイ後に実行する。最も遅いテスト層をクリティカルパス（PRのマージを止める経路）から外すことで、開発者へのフィードバック速度を保ちながら、実環境での動作確認という役割を両立できる。

この配置は、デプロイが自動化されていてデプロイ完了を契機にワークフローを起動できることが前提になる（実装は `ci-cd-pipeline-optimizer` の軸2）。Feature Flagで段階的に公開している場合は、フラグのオン・オフどちらの状態を検証するのかをシナリオごとに決めておく（`release-strategy`）。

### 4. 不安定なテストはその日のうちに扱う
偽陽性（実装は正しいのにテストが落ちる）を出すテストを放置すると、失敗の通知全体が信頼されなくなり、本当の障害も見逃されるようになる。不安定なテストを見つけたら、その日のうちに原因を直すか、`test.fixme()` などでリリース確認から一時的に外して課題化する。「そのうち直す」で放置しない。

## Playwrightの実践パターン

以下はPlaywrightを例にしているが、考え方自体はCypressやSeleniumなど他のE2Eツールにも同様に適用できる。いずれも「実装の些細な変更やタイミングのブレでテストが落ちる」という不安定さの主要な原因を潰すためのものだ。

### パターン1: ユーザー視点で要素を特定する

CSSクラスやDOM構造（`.btn-primary`、`#order-list > div:nth-child(2)`）に依存すると、見た目やマークアップを変えただけでテストが落ちる。ユーザーは要素をロールや見えているラベルで認識しているのだから、テストもそれに合わせる。

```typescript
// ❌ スタイルや構造の変更で壊れる
await page.locator(".btn-primary").click();

// ✅ ロール・アクセシブルネームで特定する
await page.getByRole("button", { name: "注文を確定" }).click();
await page.getByRole("link", { name: "注文履歴" }).click();
```

この書き方はアクセシビリティの向上にも直結する。ロールやアクセシブルネームで要素を特定できないなら、それはスクリーンリーダー利用者にとっても要素が判別しづらいということでもある。

### パターン2: 固定時間のsleepでなく状態を待つ

`waitForTimeout(3000)` のような固定時間の待機は、遅いときには失敗し、速いときには無駄に待つ。どちらの問題も、システムの処理時間に依存せず「期待する状態になるまで自動でリトライする」assertionに置き換えれば消える。

```typescript
// ❌ 環境の負荷次第で失敗も無駄な遅延も起きる
await page.waitForTimeout(3000);
const rows = await page.locator("tr").count();
expect(rows).toBe(3);

// ✅ 期待する状態が現れるまで自動的に待つ
await expect(page.getByRole("row", { name: /注文番号/ })).toHaveCount(3);
```

### パターン3: テストごとに専用データを用意する

他のテストが残したデータや状態に依存すると、単独実行・並列実行・実行順序の変更のいずれかで簡単に壊れる。各テストは自分が必要とするアカウントやデータを自分で作る。

```typescript
// ❌ 既存の固定アカウント・既存データに依存している
await signIn(page, "test-user@example.com");
await page.goto("/orders/1"); // 誰かが作った注文に依存

// ✅ テストごとに専用データを用意する
const account = await prepareTestAccount();
const order = await createTestOrder(account);
await signIn(page, account);
```

テストデータには `e2e-signup-${runId}` のように一意性と用途が分かる命名をつける。実行のたびに衝突せず、失敗時にもどのテストが作ったデータか追跡しやすくなる。

### パターン4: 認証のセットアップを分離する

すべてのテストが毎回UIからログインすると、スイート全体が遅くなるうえ、ログイン画面のちょっとした変更で無関係なテストまで一斉に壊れる。権限ごとに一度だけログインし、その結果（storageState）を保存して使い回す。

```typescript
// setupプロジェクト側で権限ごとに一度だけ実行する
setup(`authenticate as ${role}`, async ({ page }) => {
  await signInAs(page, role);
  await page.context().storageState({ path: authFile(role) });
});

// 各テストはセッションを再利用するだけ
test.use({ storageState: authFile("admin") });
```

### パターン5: スモークテストはデータ駆動で自動生成する

画面ごとにテストを手で書き足していくと、画面が増えるたびにコピペが増え、アクセス制御の抜け漏れにも気づきにくい。画面×権限のマトリクスをデータとして定義し、そこからテストを生成する。

```typescript
const screens = [
  { path: "/reports", heading: "レポート", roles: ["admin", "manager"] },
  { path: "/settings/members", heading: "メンバー管理", roles: ["admin"] },
];

for (const { path, heading, roles } of screens) {
  test(`${heading} ${path}`, async ({ page }) => {
    await page.goto(path);
    const expected = roles.includes(role) ? heading : "ダッシュボード";
    await expect(
      page.getByRole("heading", { level: 1, name: expected })
    ).toBeVisible();
  });
}
```

こうしておくと画面追加は配列に1行足すだけで済み、権限があるべきでないユーザーがアクセスできてしまう退行もスモークテストが自動的に検知する。

## 外部サービスとの連携

外部サービス（決済代行、メール配信など）が絡むフローをE2Eで検証するときは、「システム外の境界だけをモックし、バックエンド自体は本物のまま検証対象に残す」ことを徹底する。バックエンドまでモックしてしまうと、E2Eが検証しているのはモックの設定だけになり、本来の目的である「部品同士が正しくつながっているか」を確認できなくなる。

- **スタブAPI**: バックエンドの手前で外部サービスの代わりに応答する薄いスタブ。実装する挙動は必要最小限に留め、本物のAPIとの乖離を最小化する。
- **テスト支援API**: UIからは到達できない状態（データ作成、ワンタイムパスワードの取得、メールの読み取りなど）をテストから直接準備・観測するための、テスト環境限定のAPI。

```typescript
// テスト支援APIでデータを作成する
const org = await createTestOrg({ name: `e2e-signup-${runId}` });

// 非同期で届くメールを上限付きポーリングで待つ
await expect.poll(
  () => fetchLatestMail({ to: org.email }),
  { timeout: 30_000 }
).not.toBeNull();
```

本番環境を巻き込む事故を防ぐため、次の点を徹底する。

- テスト支援エンドポイントは認証必須にし、公開APIとは分離した名前空間に置く
- テスト支援エンドポイントはテスト環境でのみ有効化する
- スタブはステージング環境限定で有効にし、本番には持ち込まない
- スタブだけに頼らず、外部サービスの実アカウントを使った実連携シナリオを少数、ステージング環境で継続的に実行し、スタブと実際の挙動の乖離を検知する

## リリースパイプラインでの運用

### 環境ごとに実行するシナリオを分ける

同じテストをステージングと本番の両方で走らせる場合でも、データ作成や外部サービス呼び出しを伴うシナリオは本番では実行しない。テスト内に環境判定を埋め込み、本番では読み取り中心のスモーク確認に絞る。

```typescript
test.skip(
  process.env.E2E_ENV === "production",
  "データ作成シナリオは本番に対して実行しない"
);
```

### 失敗調査をしやすくしておく

Playwrightのtraceを有効にすれば、失敗時のスクリーンショット・コンソール出力・ネットワーク活動が自動的に残る。さらに `test.step` で操作を意味のある単位に分割しておくと、trace上でどの段階まで進んで失敗したかが一目で分かる。

### リトライは「不安定さを隠す仕組み」にしない

自動リトライ自体は有効にしてよいが、リトライを経て通ったテストを単純な「成功」として扱わない。リトライで救われたテストは不安定（flaky）としてリストに載せ、原則4（不安定なテストへの対応）に従って早期に手当てする。不安定さを可視化し続けないと、スイート全体の信頼性がじわじわ失われていく。

### スイートの規模は意識的に抑える

E2Eは全リリースを通すたびに実行され、その所要時間がリリースのクリティカルパスに直接乗る。各テストが専用データで独立している（パターン3）前提で並列実行しつつ、「主要な動線に限定する」という原則1に立ち返って、スイートが際限なく肥大化しないよう追加のたびに要否を判断する。

## レビュー・実装時のチェックリスト

- [ ] 対象のフローは認証・収益動線・スモーク確認のいずれかに該当するか（該当しないなら下位層のテストで足りないか検討する）
- [ ] バリデーションや条件分岐の詳細をE2Eで検証していないか（下位層に任せられないか）
- [ ] 要素の特定にCSSクラスやDOM構造ではなく `getByRole` 等のユーザー視点のロケーターを使っているか
- [ ] 固定時間の `waitForTimeout` ではなく、web-first assertionで状態を待っているか
- [ ] テストが他のテストの残存データ・実行順序に依存していないか
- [ ] 認証が必要なテストで、毎回UIからログインする代わりにstorageStateを再利用しているか
- [ ] 外部サービスをモックする場合、バックエンドのロジックまでモックしていないか（境界だけに留めているか）
- [ ] テスト支援API・スタブが本番環境で有効になる経路がないか
- [ ] PRパイプラインでなく、デプロイ後に実行される構成になっているか
- [ ] 不安定なテストが「リトライで通ったから成功」として放置されていないか
