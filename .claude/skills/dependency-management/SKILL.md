# Dependency Management

このスキルの前提は一つ：**依存を追加するコストは、インストールにかかる数秒ではなく、その依存が存在する限り払い続ける保守コストとリスクだ。**
AI エージェントにとって `npm install X` を打つことは一瞬の操作だが、そのパッケージはこの先ずっとプロジェクトの一部になり、脆弱性が出れば対応が必要になり、メンテナンスが止まれば自分たちで肩代わりする羽目になる。
追加する瞬間の心理的コストの低さと、追加した後に払い続けるコストの大きさは釣り合っていない。

## 新しい依存を追加するとき

### Step 1: 本当に必要か確認する

- 標準ライブラリ、あるいは既にプロジェクトが持っている依存で同じことができないか確認する。
  小さな処理のために新しい依存を足すと、その処理自体より依存の保守コストの方が大きくなることがある
- 同じ目的を持つ依存が既にプロジェクトに入っていないか確認する（似た用途のパッケージが2つ並存すると、どちらが正なのか曖昧になる）

### Step 2: パッケージの健全性を確認する

- **メンテナンス状況** — 直近のリリース日、Issue・PR への応答状況。
  長期間更新が止まっているパッケージは、今後の脆弱性対応が期待できない
- **既知の脆弱性** — `npm audit`、`pip-audit` など、言語エコシステムの標準的な監査コマンドで確認する
- **ライセンス** — プロジェクトのライセンスと非互換なライセンス（コピーレフト系など）でないか確認する。
  商用利用や配布に制約がある場合は特に注意する
- **供給元の信頼性** — ダウンロード数・スター数だけでなく、パッケージ名が有名パッケージのタイポスクワッティング（似た名前で悪意あるコードを配る手口）でないかを確認する。
  名前が紛らわしい、公式リポジトリへのリンクが無い、作成されたばかりなのに急に人気という場合は疑う

### Step 3: バージョンを固定して追加する

範囲指定（`^1.2.3` のような）ではなく、追加した時点で検証したバージョンを明示する。
自動で上がったバージョンで壊れることを防ぎ、後述の更新プロセスを通してのみバージョンが上がる状態にする。

## 既存の依存を更新するとき

### Step 1: なぜ今更新するのかを確認する

- 脆弱性対応など緊急性がある更新か、それとも定期的なメンテナンスか。
  緊急性があるなら該当パッケージだけを最短距離で上げる
- 定期メンテナンスなら、まとめて多数を一気に上げるのではなく、後述のとおり単位を絞る

### Step 2: チェンジログを読み、破壊的変更を確認する

**バージョン番号だけで判断しない。**
セマンティックバージョニングに従っていれば MAJOR の上昇（例：`2.x` → `3.x`）は破壊的変更を含む可能性が高いが、従っていないパッケージも多い。
リリースノート・CHANGELOG を実際に読み、自分たちが使っている API に影響する変更が無いかを確認する。

### Step 3: 一度に一つ（または一つの論理的な単位）だけ更新する

複数のパッケージを一括で更新して何かが壊れると、どの更新が原因か分からなくなる。
これは `debugging` が扱う「仮説を立てずに複数の変更を同時に試す」のと同じ失敗の形——原因を絞り込む手がかりを自分で消してしまう。

- 関連の薄いパッケージは1つずつ更新し、都度テストを実行する
- 同じエコシステムの関連パッケージ群（例：ビルドツールとそのプラグイン一式）はまとめて上げないと動かないことがあるので、その場合は「関連する1セット」を1つの単位として扱う

### Step 4: 更新後に確認する

- テストスイートを実行する
- 型チェック・リンターがあれば通す（API シグネチャの変更は型エラーとして表面化することが多い）
- 依存の更新は `task-breakdown` の「常に分ける」規則どおり、機能変更とは別のコミット・別の PR にする

## 大きな判断は記録する

依存を新しく採用する（特に複数の候補から一つを選ぶ）判断や、メジャーバージョンの更新を見送る判断は、後から「なぜこのライブラリなのか」「なぜまだ上げていないのか」を聞かれやすい。
後戻りしにくい・代替案を検討した判断にあたる場合は `decision-records` に残す。
