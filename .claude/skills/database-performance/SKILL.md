# Database Performance

このスキルの前提は一つ：**データベースがボトルネックになるのは、ほとんどの場合「無駄に多くのデータをストレージから読んでいる」から。** インデックスもキャッシュも分割戦略も、突き詰めれば「読むストレージ量を最小化する」という同じ目的の異なる実装手段にすぎない。個別のテクニックを覚えるより、この原則から逆算して考えると判断がぶれない。

システム全体のどこがボトルネックかをまだ特定できていない場合や、キャッシュ・非同期化・スケールアップなど対処法の優先順位そのものを検討したい場合は、performance-optimizationスキルの範囲になる。このスキルはデータベース層に入ってから、読む量を具体的にどう減らすかを扱う。

## なぜデータベースがボトルネックになりやすいか

データをどこから読むかによって、レイテンシは桁で変わる。

| 読み出し元 | 目安のレイテンシ |
|---|---|
| CPU L1キャッシュ | 約0.5ナノ秒 |
| メインメモリ | 約100ナノ秒 |
| SSD (NVMe) | 約25マイクロ秒 |
| SSD (SATA) | 約100マイクロ秒 |
| 同一リージョン内ネットワーク（往復） | 約0.5ミリ秒 |
| ネットワーク接続ストレージ | 約1ミリ秒 |

クラウド環境ではストレージの多くがネットワーク接続になっており、ローカルNVMeより数十倍遅い。この階層差があるからこそ、「読む量を減らす」「メモリに乗せる」施策の効果が大きい。

## Step 1: まず読んでいる量を観測する

推測でインデックスを足したりクエリを書き換えたりする前に、実際に何がどれだけ読まれているかを確認する。入口は3つ。

| 入口 | 何がわかるか |
|---|---|
| スロークエリログ | 閾値を超えた実クエリと発生頻度 |
| 実行計画 (EXPLAIN) | そのクエリが実際にどれだけの行・ブロックを読む見込みか |
| エンジンの状態メトリクス | キャッシュヒット率、IOPS、接続数、ロック待ち時間などの全体傾向 |

スロークエリログで「何が遅いか」を見つけ、EXPLAINで「なぜ遅いか」を確認し、メトリクスで「全体として悪化しているか」を裏取りする、という順で使うと手戻りが少ない。

## Step 2: 読む量を減らす — 4層で考える

上流（データがどこにあるかを特定する層）から下流（そもそもデータの持ち方を変える層）に向かって、効果と変更コストのバランスを見ながら検討する。

### 層1: インデックス設計

インデックスの本質は「目的のデータがストレージのどこにあるかを事前に特定し、無駄な読み取りを避ける」こと。

- **複合インデックスの順序**: 等値条件（`=`）で絞り込む列を前に、範囲条件（`>`, `<`, `BETWEEN`）で絞り込む列を後ろに置く（最左前方一致）。順序を誤ると、後半の列がインデックスとして機能しない。
- **カバリングインデックス**: SELECTで取得する列がすべてインデックスに含まれていれば、テーブル本体への追加アクセスが不要になる。

インデックスはタダではない。書込のたびに維持コストがかかるため、使われていないインデックスは読み取りに寄与せず書込を遅くするだけの負債になる。追加する前に「本当にこの検索条件で使われるか」「書込頻度に見合うか」を確認する。

### 層2: 実行計画の解読

EXPLAINを見るときに確認すべき点は3つ。

1. **スキャン方式** — インデックスを使わずテーブル全体を走査していないか
2. **読出規模の見積り** — 想定した絞り込みが本当に効いているか（見積り行数が実際の結果件数と大きく乖離していないか）
3. **一時ストレージへの書き出し** — ソートや集計がメモリに収まらず、ディスクに溢れていないか

意図した実行計画にならない場合、オプティマイザが誤った判断をしていることがある。統計情報の再集計、結合順を明示するヒント句、あるいはクエリ自体を分割して単純化することで対処できる。

### 層3: アプリケーション設計

インデックスや実行計画が最適でも、アプリケーション側の呼び出し方が非効率だと読む量は減らない。

- **N+1クエリの解消**: ループの中で1件ずつ問い合わせるのではなく、結合やIN句でまとめて取得する（Eager Loading）。往復回数そのものを減らす。
- **深いOFFSETを避ける**: `SELECT * FROM items ORDER BY id LIMIT 20 OFFSET 100000` のようなクエリは、100,000件を読んで捨てたうえで20件だけ返している。ページ番号ではなく「最後に取得した位置（IDや日時）」を条件にするカーソル方式に変えると、毎回の読取量が一定になる。
- **同一データへの重複アクセスを避ける**: 同じマスタデータをリクエスト内で何度も引いていないか確認する。冒頭で一括取得してメモリに保持すれば、同一リクエスト内の重複読取をなくせる。
- **ORMが実際に発行しているSQLを確認する**: 便利メソッド（例: Railsの`in_batches`）はバッチの回数だけ処理を繰り返す。1回あたりが軽くても、バッチ内に高コストな処理が含まれていると、回数分そのコストを払うことになる。ORM経由の呼び出しほど、実際に流れているSQLをログやEXPLAINで確認する習慣が要る。

### 層4: データの持ち方を変える

ここまでの層で足りない場合、最後の手段としてデータの持ち方そのものを変える。ただしどちらも「対価」を伴う選択であり、気軽に導入しない。

| 手法 | メリット | 対価 |
|---|---|---|
| 非正規化 | 読取が単純な参照になる | 更新時に複数箇所の整合性を維持する必要があり、不整合リスクを抱える |
| 事前集計（サマリーテーブル） | 大量スキャンが数行の読取になる | 集計軸が固定される。鮮度は更新頻度に依存し、リアルタイム性を失う |

## Step 3: キャッシュヒット率を維持する

バッファプールなどのキャッシュにワーキングセット（頻繁にアクセスされるデータ）が乗っていれば、そもそもストレージへのI/Oが発生しない。キャッシュヒット率が下がってきたら、メモリの増設だけでなく、全件走査するようなクエリがキャッシュを押し出していないかも確認する。ヒット率はストレージ階層の中で一番効果が大きい場所なので、他の層をいじる前に劣化していないか定期的に見ておく価値がある。

## Step 4: 単一データベースの限界を超える

Step 1〜3で読む量を最小化してもなお足りない場合に検討する、より構造的な対処。

| 戦略 | 内容 | 制約 |
|---|---|---|
| リードレプリカ | 読み取りを複数のレプリカに物理分散する | レプリケーション遅延により、レプリカ側では結果整合性（最新でない可能性）を許容する必要がある |
| 機能分割 | ドメインやテーブル群ごとに別のデータベースへ分ける | 分割した境界をまたぐ結合・トランザクションができなくなる |
| シャーディング | テナントIDやユーザーIDなどのキーで複数のデータベースに分割する | 同上。加えて、後から分割方針を変更する（リシャーディング）のは非常にコストが高い |
| OLTP/OLAP分離 | 細粒度の読み書き（OLTP）と大量データの集計（OLAP）を専用エンジンに分ける | データウェアハウス、リアルタイムOLAPエンジン、HTAPなど専用製品の選定・運用コストが増える |

これらはどれも一度導入すると後戻りが難しい設計判断であり、Step 1〜3で解決できないか（インデックス・クエリ・キャッシュで十分か）を先に潰してから検討する。特にシャーディングは「後から変更しにくい」代表格なので、データ量やアクセスパターンの将来予測に基づいて慎重に判断する。

## 適用範囲外

以下はこのスキルの主題ではない。関連する相談を受けたら、その旨を伝えたうえで別の観点で扱う。

- リレーショナルデータベースのサーバーパラメータ（バッファサイズ、コネクション数上限など）のチューニング
- 書込性能そのものの改善（このスキルはインデックスの書込コストなど関連箇所には触れるが、書込最適化が主題の場合は別途検討する）
- NoSQLデータベース固有の最適化（読む量を最小化するという考え方自体は概ね通用するが、データモデルが大きく異なるため個別の検証が要る）

## 実装チェックリスト

- [ ] スロークエリログ・EXPLAIN・エンジンメトリクスのいずれかで、実際に読まれている量を観測した
- [ ] 複合インデックスの列順（等値→範囲）を確認した
- [ ] SELECT対象列だけでカバリングインデックスが組めないか検討した
- [ ] EXPLAINでスキャン方式・見積り行数・一時ストレージ書き出しの3点を確認した
- [ ] N+1クエリが発生していないか確認した
- [ ] 深いOFFSETページネーションをカーソル方式に置き換えられないか検討した
- [ ] ORMが実際に発行しているSQLを確認した
- [ ] 非正規化・事前集計を導入する場合、その対価（整合性・鮮度）をチームで合意した
- [ ] キャッシュヒット率が劣化していないか確認した
- [ ] リードレプリカ・分割・OLTP/OLAP分離が本当に必要か、Step 1〜3を先に潰したうえで判断した
