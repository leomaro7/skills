# Decision Records

このスキルの前提は一つ：**書き残されなかった決定は、次に読む人にとって存在しなかった決定と同じになる。**
会話の中でどれだけ丁寧に検討し、どれだけ強く合意したとしても、その経緯が文書として残らなければ、次にその決定に触れた人（人間でも AI エージェントでも）は「なぜこうなっているのか」をゼロから推測することになる。
運が良ければ正しく推測できるが、悪ければ既に検討済みの案をもう一度提案し、既に却下した理由を知らないまま採用してしまう。

AI 駆動開発ではこの問題が特に切実になる。
**AI エージェントのセッションは会話が終われば経緯を持ち越さない。**
人間のチームなら記憶や雑談で薄く残る「なぜあの時ああ決めたか」が、AI エージェント相手には一切残らない。
次のセッションは、コードと（記録されていれば）ドキュメントだけを見て判断することになる。

## いつ書くか

次のいずれかに当てはまる決定は書く価値がある。

- **後戻りしにくい。**
  一度採用すると、覆すのに大きなコストがかかる（データモデル、公開 API の形式、採用した技術・ライブラリ、大きな方針転換）
- **後から「なぜこうしたのか」と聞かれそうな。**
  一見して自明でない判断、直感に反する選択（例：あえてシンプルな方法を選んで高度な方法を見送った）
- **検討した末に採用しなかった選択肢がある。**
  有力な代替案を意図的に却下した場合、その理由を残さないと、後から同じ代替案が「まだ検討されていない新しい提案」として再浮上する

**逆に、些細な・すぐ変更できる決定には使わない。**
変数名の付け方、関数の分割単位のような、コード自体を読めば分かる・すぐやり直せる判断まで記録すると、誰も読まない文書の山になり、本当に重要な記録が埋もれる。
迷ったら「この決定が、コードを読むだけでは分からない理由を持っているか」で判断する。

## どこに書くか

リポジトリ内の `docs/decisions/`（無ければ近い場所、例えば `docs/adr/`）に、決定1件につき1ファイルを置く。
ファイル名は連番か日付で並び替えられる形にする（例：`0001-use-worktree-for-parallel-agents.md`）。
会話ログやコミットメッセージだけに残すのではなく、**コードと同じ場所に、コードと同じように検索・参照できる形で**置くのが要点——別のツールや別の場所を探しに行かないと見つからない記録は、結局読まれない。

## 書式

数分で書ける軽量な形式にする。
厚い設計文書ではない。

```markdown
# <決定の短いタイトル>

Status: Accepted <!-- Proposed / Accepted / Superseded by 000X -->

## Context
何を決める必要があったか。制約や前提（技術的制約、期限、既存システムの事情）。

## Decision
採用した案を一文で。

## Alternatives
検討して採用しなかった案と、それぞれ採用しなかった理由。
ここが最も価値が高い——後から「なぜXにしなかったのか」と聞かれたとき、
ここを読めば再検討の手間なく答えられる。

## Consequences
この決定によって、今後何がやりやすくなり、何がやりにくくなるか。
```

**Alternatives（検討したが採用しなかった案）を省略しないこと。**
Decision だけを書くと「何を選んだか」しか残らず、「なぜそれ以外を選ばなかったか」という、後から最も聞かれる質問に答えられない。

## 決定が覆ったとき

**古い記録を消さない。**
Status を `Superseded by 000X` に変え、新しい決定の記録から古い記録へも逆にリンクする。
これにより「一度 A を選び、後で B に変えた」という経緯そのものが残り、次に誰かが A と B の間で迷ったときに両方の判断材料を読める。
削除してしまうと、以前 A を検討して却下した事実まで消え、同じ議論が繰り返される。

## 関連スキル

`modifiability-review` は決定を一貫させ記録することを変更容易性の防止策として要求している——このスキルがその記録先と書式を提供する。
`database-selection`・`release-strategy`・`performance-optimization`（後戻り困難な判断）は、いずれもここで言う「後戻りしにくい決定」を生み出す場面であり、それらのスキルで結論が出た後にこのスキルへ引き継ぐ。
