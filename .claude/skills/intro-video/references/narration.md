# 読み上げ向け日本語の書き方

台本は人間が読む文章ではなく、音声合成エンジンが声に変換し、視聴者が**耳だけで**受け取る文章だ。
書き言葉としての正しさよりも、聞いて意味が取れることを優先する。

## 1. 一文を短く切る

耳は係り受けを保持できない。
読点でつないだ長い文は、最後まで聞いた頃には主語を見失う。

**一文は40〜60文字まで。**
長くなったら、接続助詞（〜ので、〜が、〜ため）で切って二文にする。

- ❌ 「このスキルは既存の資料を読み取って構成を組み替えたうえでナレーションを生成し、スライドと結合して動画にするので、資料さえあれば数分で紹介動画が作れます。」
- ✅ 「このスキルは、資料を読み取って紹介動画の構成に組み替えます。
  ナレーションとスライドを生成し、動画として結合します。
  資料さえあれば、数分で完成します。」

句点では自然に間が入る。
文を切ることは、そのまま聞き手に理解の時間を渡すことでもある。

## 2. 強調したい語の前に読点を置く

読点は短い間になる。
刺したい語の直前に置くと、その語が立つ。

- 「重要なのは、順番です。」
- 「ここで効いてくるのが、台本とスライドを分けておくことです。」

ただし多用すると全体が間延びする。
1スライドに1箇所まで。

## 3. 記号・英略語・数字はカタカナに開く

**これが台本とスライドを別ファイルにしている最大の理由だ。**
記号や英字の読み方は音声合成エンジンごとに違い、macOS の Kyoko と Windows の Haruka で結果が揺れる。
読みを固定したい箇所は、台本側だけカタカナで書く。
スライドの表記は元のままでよい。

| スライドの表記 | 台本に書く読み |
|---|---|
| `CI/CD` | シーアイ・シーディー |
| `README` | リードミー |
| `mp4` | エムピーフォー |
| `3〜4個` | 3から4個 |
| `100%` | 100パーセント |
| `~/.claude/skills/` | ホームディレクトリの、ドットクロード、スキルズ |
| `v2.1.0` | バージョン2.1.0 |

判断基準は「この表記を、二つの OS が同じように読む保証があるか」。
無いなら開く。

**ニューラル系のエンジン（`local` / `voicevox` / `neural`）では、この対処はほぼ不要になる。**
ニューラル音声は `README` も `CI/CD` も文脈から正しく読む。
ただしカタカナで書いても不自然にはならないので、どちらのエンジンで出すか決まっていない段階では開いておくほうが安全。

**英単語も同じ。**
日本語音声は英語を日本語の音韻で読むので、`GitHub Actions` は「ギットハブ アクションズ」と書いたほうが安定する。
ただし開きすぎると台本が読みにくくなるので、**固有名詞と略語だけ**に絞る。

**ファイルパスやコマンドは、そもそも読み上げない。**
聞いても書き取れない。
スライドに実物を表示し、台本では「右に出ているコマンドを実行します」と指し示すだけにする。

## 4. 「です・ます」で書き、体言止めを使わない

スライドは体言止めでよいが、台本は文末まで言い切る。
体言止めは音声にすると唐突に途切れて聞こえる。

- ❌ 「三つのステップで完成。」
- ✅ 「三つのステップで完成します。」

## 5. 指示語をスライドの中身に向けて使う

ナレーションとスライドの対応関係は、指示語で明示すると視聴者が迷わない。

- 「いま出ている三つのうち、二つ目が要です。」
- 「左側が変更前、右側が変更後です。」

逆に、スライドに無いものを指示語で指してはいけない（「これが問題です」とだけ言って画面に何も無い状態）。

## 6. 文末表現を並べない

1スライドずつ台本を書くと、全スライドの文末が「〜できます」で揃いがちになる。
通しで聞くと単調で、内容が入ってこなくなる。
書き終えたら文末だけを縦に読んで、三連続していたら変える。

## 7. スライドの文字を読み上げない

見出しに書いた語をそのまま台本の冒頭に置くのは、最も起きやすい失敗だ。
**見出しは「何の話が始まるか」を目に、台本は「その中身」を耳に届ける**という分担にする。

- スライド見出し: 「台本が主、スライドが従」
- ❌ 台本: 「台本が主で、スライドが従です。」
- ✅ 台本: 「情報を運ぶのはナレーションの役目です。
  画面に出ているのは、話についていくための手がかりだと考えてください。」
