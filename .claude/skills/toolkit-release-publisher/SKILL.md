# Toolkit Release Publisher

GitLab で共有しているツールキット（Skill・エージェント・MCP が混在するリポジトリ）の新バージョンを公開する。
差分からリリースノートの下書きを作り、次バージョンを根拠付きで提案し、**ユーザーが確認・確定してから** `glab release create` でタグとリリースを作成する。
公開すると `/-/releases?format=atom` 経由で購読者に通知が届く。

## 前提条件

開始前に確認する（満たしていなければ下記の手順で解消するか、ユーザーに伝えて止まる）：

- **カレントディレクトリがリポジトリルートであること。**
- **公開対象が正しいリリースブランチであること。** 既定のブランチ名は `main` または `master` のどちらの場合もある。`git branch --show-current` で現在のブランチを確認し、リポジトリの既定ブランチを判定する：

  ```
  git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null | sed 's@^origin/@@'
  ```

  これが取れなければ `main` → `master` の順にローカルブランチの有無を確認してフォールバックする。

  **現在のブランチが既定ブランチと違う場合は、次のどちらにするかをユーザーに確認する：**

  - **A: 既定ブランチへ切り替えて公開（推奨）** — まず `git status -s` で未コミット変更がないか確認する。**未コミット変更があれば停止し、コミット／stash をユーザーに促す**（勝手に stash しない）。クリーンなら `git switch <既定ブランチ>` → `git fetch origin` → `git merge --ff-only origin/<既定ブランチ>` でリモート最新に同期する。
  - **B: 現在のブランチを直接公開** — 切り替えず、ステップ 7 の `glab release create` に `--ref <現在のブランチ>` を付けて公開する。

  **公開したい変更が既定ブランチにまだマージされていない場合は、マージの完了を待ってから `git fetch origin` で取り込み直す**（このスキルはマージ自体は代行せず、ユーザーのマージを待つ）。

- **`glab` がインストール・認証済みであること。** `glab auth status` で確認する。
  - `glab` 未インストールの場合は、OS に応じてインストールを案内・実行する（ユーザーの承認を得てから）：
    - **macOS**: `brew install glab`
    - **Linux**: `brew install glab`、または Debian/Ubuntu 系なら公式 apt リポジトリ、その他は[リリースバイナリ](https://gitlab.com/gitlab-org/cli/-/releases)を配置。
    - **Windows**: `winget install glab.glab`、または `scoop install glab` / `choco install glab`。
  - インストール後は `glab auth login` で認証する（ユーザー自身の操作が必要なので、`! glab auth login` をプロンプトで実行するよう案内する）。

## ワークフロー

### 1. 現在のバージョンを把握する

```
git describe --tags --abbrev=0
```

直近のタグを確認し、**既存タグの接頭辞スタイル（`v` の有無）に提案を揃える**（例: 既存が `v1.2.0` なら次も `v` 付き、`1.2.0` なら付けない）。
タグが 1 つも無ければ初回リリース。ステップ 4 で扱う。

### 2. 差分を集める

ベースは **既定で直近のリリースタグ → HEAD**。
ユーザーが「dev と main の差分で」のように範囲を指定したら、その指示に従う（例: `main..dev`）。

```
git log <base>..HEAD --no-merges --oneline
git diff <base>..HEAD --stat
```

### 3. 部品ごとのバージョン変更を拾う

変更された `SKILL.md` や MCP 設定ファイル（`*.json` / `*.toml` などの `version` 行）の差分を確認し、
**「部品名 + 版」** を後のノートに併記する。

```
git diff <base>..HEAD -- '**/SKILL.md' '**/*.json' '**/*.toml' | grep -iE '^\+.*version|^\+name:'
```

部品の種別はノートのアイコンに対応させる：🧩 Skill / 🤖 エージェント / 🔌 MCP。

### 4. 次バージョンを提案する（セマンティックバージョニング）

差分の内容から次バージョンを **理由とセットで** 提案する。**確定はユーザーが行う**ので、ここでは提案に留める。

- **破壊的変更あり** → メジャー（例: `v1.2.0` → `v2.0.0`）
- **後方互換の機能追加** → マイナー（例: `v1.2.0` → `v1.3.0`）
- **修正のみ** → パッチ（例: `v1.2.0` → `v1.2.1`）
- **現在版が `0.x` の場合**は、破壊的変更でもマイナー止まりにする慣習に従う（`0.3.0` → `0.4.0`）。
- **初回リリース**（タグなし）は `v0.1.0` か `v1.0.0` のどちらにするかをユーザーに尋ねる。
- 判断に迷う場合は **patch / minor / major の 3 案を並べて** それぞれの根拠を示し、ユーザーに選ばせる。

### 5. リリースノート下書きを生成する

`assets/release-notes-template.md` を雛形に、`release-notes-<TAG>.md` をリポジトリルートに生成する。
形式は [Keep a Changelog](https://keepachangelog.com/) に準拠する。`<TAG>` はステップ 4 で提案したバージョン（接頭辞スタイルを揃えたもの）、日付は公開日（YYYY-MM-DD）。構成は：

```
## [<TAG>] - <YYYY-MM-DD>

<このバージョンの変更を一言で（誰でも分かる平易なサマリ）>

### Added（追加）
### Changed（変更）
### Deprecated（非推奨）
### Removed（削除）
### Fixed（修正）
### Security（セキュリティ）
```

執筆方針：
- **Keep a Changelog の 6 カテゴリ（Added / Changed / Deprecated / Removed / Fixed / Security）に変更を振り分ける。** 各見出しには日本語の補足を添える。
- **該当する変更がないカテゴリは、見出しごと削除する**（空のまま残さない）。
- **誰が読んでも分かる平易な言葉で書く。** 専門用語には一言補足を添え、利用者にとって何が嬉しい／何が変わるのかを書く。
- **破壊的変更（既存の使い方が壊れる変更）は、該当カテゴリ（多くは Changed か Removed）の行頭に `**破壊的:**` を付けて明示し、冒頭サマリでも必ず触れる。**
- 各行には、ステップ 3 で拾った「部品名 + 版」を併記する（種別の目印に 🧩 Skill / 🤖 エージェント / 🔌 MCP を添えてよい）。

### 6. 停止してレビューを依頼する（必須チェックポイント）

下書き全文と、**提案バージョン + その根拠**をユーザーに提示する。
バージョンと内容の **確認・修正を待つ**。**ここで必ず一度止まる。**
ユーザーが修正を求めたら下書き／提案を直し、再度提示する。

### 7. 確認後に公開する

ユーザーが**明示的に「公開してよい」**と言ってから、確定した `<TAG>` で実行する：

```
glab release create <TAG> --name "<TAG>" --notes-file release-notes-<TAG>.md
```

実行後、手元にタグを取り込めることを案内する：

```
git fetch --tags origin
```

### 8. 完了報告

ユーザーに次を伝える：
- リリースを作成したこと（`<TAG>`）。
- 購読者へ `/-/releases?format=atom` フィード経由で通知が届くこと。
- リリースページの URL（リポジトリの `/-/releases`）。

## 厳守事項（ガードレール）

- **バージョン番号は根拠付きで提案してよいが、確定は必ずユーザーが行う。** 承認・上書きなしに採番しない。
- **下書き生成後は必ず一度停止し、ユーザーの確認・修正を待つ。** 確認なしに公開しない。
- **`glab release create` はユーザーが明示的に「公開してよい」と言ってから実行する。**
- **リリースノートは Keep a Changelog 形式に準拠する。** 破壊的変更は冒頭サマリで触れ、該当カテゴリの行頭に `**破壊的:**` を付けて明示する。
- **誰が読んでも分かる平易な言葉で書く。** 専門用語には一言補足を添える。
- **現在のブランチが既定ブランチ（main / master）と違う場合は、勝手に切り替え・stash・マージをしない。** 切り替え方針をユーザーに確認し、未コミット変更があれば停止する。
