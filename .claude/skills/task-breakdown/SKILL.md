# Task Breakdown

このスキルの前提は一つ：**タスク分解は実装前の準備作業ではなく、プルリクエストの粒度そのものを決める設計行為だ。** ここでどう切るかによって、後続のレビューのしやすさ、見積もりの当たりやすさ、失敗したときの取り消しやすさが決まる。分解が粗いと大きすぎるPRが生まれ、分解が細かすぎると単体で意味を持たないPRが生まれる。狙うのはその中間、「単体で出荷可能で、単体で安全に取り消せる」単位だ。

## なぜ分解に時間をかける価値があるか

- **見積もりが当たる。** 「機能全体」を一つの塊で見積もると誤差が大きいが、具体的な小タスクを積み上げると誤差が小さくなる。
- **手戻りが減る。** コードを書く前にタスクリストをレビューしてもらえば、考慮漏れを一番安いタイミング（実装前）で発見できる。
- **PRが1つのことに集中する。** 分解したタスクをそのままPRの単位にできるので、レビュアーが「このPRは何をしているか」で迷わない。
- **進捗と引き継ぎが可視化される。** チェックリスト化されたタスクは、人にもAIエージェントにも「次に何をすべきか」がそのまま伝わる。分解が粗いままだと、AIエージェントに渡すタスクの範囲や前提（コンテキスト）も曖昧になり、余計な確認往復や誤った変更範囲を招きやすい。

## 良いタスクの条件

一つのタスクは、以下の4条件を**同時に**満たすことを目指す。どれか一つでも欠けるなら、まとめ直すか分割し直す。

1. **壊さずにマージできる** — 単体でmainに統合でき、マージ後もアプリケーションが正常に動作する
2. **テストを含む** — 実装とそのテストは同じタスクで出荷する。テストを「後で書く」別タスクに分けない
3. **単独でrevertできる** — このタスクだけ取り消しても、他のタスクが壊れない
4. **一度に読み切れる** — レビュアーが中断せず全体を理解できる分量に収まっている

## タスクをまとめるか分けるか判定する

2つのタスク（またはタスク候補）があるとき、次の3ステップを**順番に**当てる。途中でどれか一つでも「まとめる」判定になったら、そこで確定する。

1. **独立性を確認する** — タスクAなしでタスクBは正しく動くか？ 動かないなら、まとめる。
2. **完結性を確認する** — タスクAは単体で意味のある、マージ可能な単位か？ そうでない（それ単体では中途半端）なら、意味を持たせるタスクへまとめる。
3. **revert影響を確認する** — タスクAをrevertすると、タスクBも壊れるか？ 壊れるなら、まとめる。

3ステップすべてを「まとめない」で通過して初めて、2つは別タスクとして分けてよい。

判断に迷ったときのために、繰り返し現れるパターンを覚えておくと速い。

**常にまとめる：**
- 実装とそのテスト
- APIエンドポイントとそのルーティング
- データモデルとそのマイグレーション

**常に分ける：**
- リファクタリングと新機能（挙動を変えない変更と変える変更を同じPRに混ぜない）
- ライブラリ更新と機能開発
- パフォーマンス改善と機能開発
- データマイグレーションと機能開発
- Feature Flagのライフサイクルの各段階（コード追加 → 有効化 → フラグ削除。各段階の設計と段階的ロールアウトの手順は `release-strategy`）
- 互いに依存しない複数の機能

この一覧に当てはまらない組み合わせは、3ステップの判定に戻って個別に考える。

## 分解の手順

分解は一発で完成させるものではなく、反復して精度を上げていくものだ。最初のリストが粗くても構わない。

1. **要件からたたき台を作る。** ざっくりした要件を、そのままIssueのタスクリストとして書き出す。例：「ユーザーデータの一覧を返すREST APIを追加する」
2. **単体で出荷できるスライスに展開する。** たたき台の各項目を、上記の4条件を満たす単位まで分解する。例：一覧取得・絞り込み・ページネーション・ソートを、それぞれ独立したタスクに分ける
3. **職種をまたいでレビューする。** コードを書き始める前に、実装者以外（他のエンジニア、必要ならPM・デザイナーなど）にリストを見てもらい、曖昧な項目を具体化する。ここでの指摘は実装後の手戻りより圧倒的に安い
4. **実装中も分割し続ける。** 実装を進めると、事前には見えなかった複雑さや隠れた依存が明らかになる。それをリストに反映し、肥大化しそうなタスクはその場で分割する。最初のリストに固執しない

## 依存関係を整理し、並列化できる単位を見つける

タスクリストができたら、各タスクが何に依存しているかを洗い出す。依存のないタスク同士は、複数の人や複数のAIエージェントが同時に着手できる。

例（ユーザー一括登録機能）：

```
Task1: ドメインモデル定義        ← 依存なし。最初に着手
Task2: パーサー実装              ← Task1に依存
Task3: バリデーター実装          ← Task1に依存
                                    (Task2とTask3は互いに独立 → 並列実装可能)
Task4: サービス層（パース+検証を統合） ← Task2, Task3に依存
Task5: APIエンドポイント          ← Task4に依存
```

タスクを提案するときは、依存関係を明示したこのような一覧（または依存グラフ）を添える。それだけで「今どれから着手できるか」「どれとどれを並行して進められるか」が一目で判断できる。

## Issueに落とし込む

分解と依存関係の整理が終わったら、タスクごとにIssueを作る。チェックボックスの箇条書きのままでは、担当者・議論・進捗をタスク単位で追跡できない。GitHubを使っている場合、Sub-issuesで親子関係を、依存関係機能で着手順を表現できる。

- **親Issue** — 機能全体の背景・目的と、分解したタスクの全体像（子Issueへのリンク一覧）を記載する
- **子Issue** — 個別タスクの要件・完了条件・依存する（される）Issueを明記する

テンプレートと具体的な使い方は `references/issue-templates.md` を参照。実際にIssueを作成する（`gh issue create` など）前には、分解案を人間に提示して確認を取ること — 分解の粒度や依存関係の見立てが誤っていると、後続のタスクや他のエージェントの作業範囲に影響するため。

## 進め方の要約

1. ユーザーから機能・要件を聞き、要件をそのままタスクリストのたたき台にする
2. 各タスクに4条件を当てはめ、3ステップ判定でまとめ直す/分け直す
3. 出荷可能なスライス単位まで分解し、粗すぎる項目や曖昧な項目を具体化する
4. 依存関係を整理し、並列化できる組を洗い出す
5. 親Issue・子Issueの形にまとめて提示し、ユーザーの確認を得てからIssue化する
