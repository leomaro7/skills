# Issueテンプレート

タスク分解の結果をIssue化するときに使うテンプレート。分解した内容をこの形にまとめ、ユーザーに確認を取ってから `gh issue create` などで実際に作成する。

## 親Issue

機能全体の背景・目的と、タスク一覧の全体像を示す。個別タスクの実装詳細は書かない（それは子Issue側の責務）。

```markdown
## 背景・目的

<なぜこの機能が必要か。何を解決するか>

## スコープ

<この機能に含むこと／含まないこと>

## タスク一覧

- [ ] #<子Issue番号> ドメインモデル定義
- [ ] #<子Issue番号> パーサー実装（ドメインモデル定義に依存）
- [ ] #<子Issue番号> バリデーター実装（ドメインモデル定義に依存）
- [ ] #<子Issue番号> サービス層実装（パーサー・バリデーターに依存）
- [ ] #<子Issue番号> APIエンドポイント実装（サービス層に依存）

## 依存関係図

<並列化できる組と、着手順が分かる図または箇条書き>
```

## 子Issue

個別タスクの要件・完了条件・依存関係を明記する。「何をもって完了とするか」を曖昧にしない。

```markdown
## 概要

<このタスクで何を実装するか、一文で>

親Issue: #<親Issue番号>

## 依存関係

- 依存する: #<Issue番号>（このIssueより先に完了している必要がある）
- 依存される: #<Issue番号>（このIssueの完了を待っている）

依存がなければ「なし（着手可能）」と明記する。

## 要件

<具体的な実装要件を箇条書きで>

## 完了条件

- [ ] <実装が満たすべき条件>
- [ ] テストが書かれ、パスしている
- [ ] <このタスク固有の受け入れ基準>
```

## 使うときの注意

- 子Issueの「完了条件」には必ずテストの完了を含める（実装とテストは同じタスクで出荷するため）。
- 依存関係は一方向だけでなく両方向（依存する/依存される）を書くと、親Issue側の依存関係図と突き合わせやすい。
- GitHubのSub-issues機能を使える場合は、親Issue側でSub-issuesとして子Issueを紐付けると、子Issueの完了状況が親Issueに自動集約される。
